## 3. Базовая линия CRM — порог, который суррогат обязан бить

Обучена на настоящем отклике базового прогона. **Подгонка занимает 8 секунд.**

Разрез оси времени: 168 интервалов на обучение, **56 отложенных** на замер. Метрики приёмки считаются только на отложенной части.

| | R² | Spearman | MAE | медианная отн. ошибка |
|---|---|---|---|---|
| **Отложенная (приёмка)** | **0.9482** | **0.9787** | 52.7 м³ | 4.88% |
| Обучающая (диагностика) | 0.9694 | 0.9815 | 34.5 м³ | 3.75% |

Разрыв train−holdout 0.021 — переобучения нет. Фонд: 48 добывающих × 40 нагнетательных.

### Два результата, которые не надо переоткрывать

**Ограничение знака коэффициентов несущее.** Свободная подгонка даёт train R² 0.99 при holdout R² **−5.3** — чистое запоминание. Запрет отрицательной аллокации (`f ≥ 0`) поднимает holdout до +0.87.

**Материальный баланс накладывается в ходе подгонки, а не после.** Без ограничения 17 из 41 нагнетательной нарушают баланс (максимум суммы 4.14). Пересчёт коэффициентов уже сошедшейся модели роняет R² до **−2.56**, потому что свободный член остаётся подогнанным под старые значения.

### Чего эти метрики НЕ доказывают

Это важно, чтобы не сравнить суррогат с CRM некорректно:

- метрики измерены **при одной программе закачки** — показан перенос с ранних интервалов на поздние, а не с одного сценария на другой, а оптимизатору нужно именно второе;
- **ранговой корреляции по ЧДД здесь нет и быть не может**: сценарий один, ранжировать нечего. Приведённая Spearman — по объёмам жидкости, это другая величина. Полноценный порог появится только на датасете;
- отложенная часть систематически «богаче» обучающей (закачка растёт 50.1k → 58.2k м³/мес, фонд нагнетательных 27 → 41), часть holdout-качества — экстраполяция тренда;
- 22 скважины с неполной историей исключены из подгонки;
- **CRM моделирует жидкость, а деньги сидят в обводнённости** — как базовая линия по нефти он слаб по построению.

## 4. Как продолжить: конкретные шаги

### Шаг 1. Развернуть окружение и данные

```bash
git clone https://github.com/aios-hack/aios.git
git clone https://github.com/aios-hack/docs.git         # соседним каталогом, код ищет ../docs
git clone https://github.com/aios-hack/dataset-700.git  # 700 прогонов и checkpoint
cd aios
python3 -m venv .venv && .venv/bin/pip install -e ".[dev,ml]"
cp -R ../dataset-700/dataset-main ../dataset-700/dataset-extra-500 data/
```

Экстра `ml` тянет torch и numpy; для обучения на CPU этого достаточно, GPU не требуется. `docker pull openporousmedia/opmreleases:latest` нужен только если досчитывать датасет или гонять внешнюю верификацию — для обучения на готовых прогонах Docker не нужен.

Если датасет всё-таки надо расширять, запуск генерации (скрипт `build_dataset.py` в корне, если его нет — см. §5):

```bash
AIOS_DATASET_WORKERS=8 AIOS_DOCS_ROOT=/путь/к/docs python build_dataset.py
```

Число воркеров подбирается под железо. **Важно:** Flow внутри контейнера сам многопоточный, поэтому воркеров имеет смысл ставить примерно `ядра / 2`, а не по числу ядер — иначе прогоны отбирают ядра друг у друга. Замер: на 16 ядрах при конкуренции прогон замедлялся с 513 до 1823 с, то есть в 3.5 раза.

Для объёма 200–400 прогонов правьте `PlanConfig` в `backend/contexts/simulation/domain/perturbation_design.py` — параметры `n_level_scenarios`, `n_unreachable_scenarios`, `n_shutdown_scenarios`, `n_conversion_scenarios`.

### Шаг 2. Обучить модель (задача 34)

Требования контракта (`docs/context/08_contracts.md` §5, `07_concept.md` §5.1):

- предсказывать **три величины раздельно**: факт добычи жидкости, обводнённость, приёмистость. **Дебит нефти напрямую не предсказывать** — он выводится как `q_нефти = q_жидкости × (1 − обводнённость)`;
- вход — только целевые накопления с 1994 плюс λ своего окна (`backend/contexts/surrogate/domain/features/` это уже строит);
- выход — два контрактных типа, `IntervalResponse[224]` и `StateAtDate[371]` (`backend/contexts/surrogate/application/adapter.py` это уже принимает);
- детектор выхода за обучающий диапазон уже реализован в `backend/contexts/robustness/domain/ood.py`; после формирования train-split нужно построить `TrainingDomain` и возвращать `ood_score` вместе с каждым прогнозом;
- модель должна иметь стабильный `version`/идентификатор checkpoint, который внешний цикл использует при переоценке после дообучения.

**Главная ловушка** (§5.1.1): модель, обученная «управление → дебит» в лоб, выучит тождество `дебит ≈ целевая уставка`, покажет отличный MAE, а оптимизатор поверх неё скажет «поднять всё» и обвалит давление. **Суррогат обязан моделировать недостижимость цели** — то есть случаи, когда скважина упирается в предел по забойному давлению и не добирает заданный режим. В датасете такие сценарии есть специально (семейство «недостижимые уставки»).

Численное подтверждение, что ловушка реальна: на базовом прогоне **11 226 недоборов цели, из них 11 166 в режиме BHP-лимита** при нулевых нарушениях самих пределов давления.

### Шаг 3. Выполнить реальную приёмку готовыми метриками (задача 36)

Оптимизировать на **ранжирование, а не на MAE** (§5.2). Реализация в `backend/contexts/surrogate/domain/metrics/` считает ранговую корреляцию по ЧДД, precision@k, regret на top-k, обводнённость и обязательные метрики `StateAtDate`.

Порог приёмки: **суррогат обязан бить CRM по ранговой корреляции**, иначе отвергается. Функция сравнения готова — `compare_to_baseline` в `backend/contexts/surrogate/domain/crm/`.

## 5. Технические детали окружения

**Зависимости.** numpy и scipy в проекте отсутствуют — CRM написан на stdlib. Если для суррогата нужны тяжёлые библиотеки, добавлять их своей строкой в `pyproject.toml`, не трогая чужие.

**Пути к данным.** Дек и эталонный расчётчик ищутся через `AIOS_DOCS_ROOT`, сохранённый базовый прогон — через `AIOS_BASE_RUN_DIR`. Резолверы в корневом `conftest.py`.

**Скрипт генерации** — `build_dataset.py` в корне репозитория. Тот же запуск воспроизводится и через публичные функции:

```python
from pathlib import Path

import conftest
from bridge.dataset import DatasetGenerator
from bridge.dataset_plan import build_plan

generator = DatasetGenerator(conftest.model_z_dir(), Path("data/dataset-main"),
                             max_workers=8, timeout_seconds=7200.0)
plan = build_plan(generator.base_schedule(), seed=20260816)
report = generator.build(plan)
```

**На Windows** обязательно `sys.stdout.reconfigure(encoding="utf-8")` — иначе русский вывод падает на cp1252.

**Правила проекта, которые нельзя нарушать:**

- моков нет: компонент, который не может посчитать, бросает исключение, а не возвращает `0.0` или случайный тензор;
- синтетические данные допустимы только для проверки формы, **никогда в метриках качества**, и помечаются флагом в метаданных;
- `data/` в git не кладётся, адресуется хешами;
- `contracts/` правит только интегратор.

Число перетоков попадает в отчёт: 298 интервалов, худший −15.84 т.

| Состояния фонда | точность `0.998`, BHP-лимит F1 `0.962`, precision переходов `0.935`, recall `0.975` |

**Как это читать.** Модель обучена и воспроизводима, состояния фонда и обводнённость она держит. Слабое место — ровно то, ради чего суррогат существует: ранжирование. Spearman `0.737` при precision@1 `0.0` означает, что общий порядок сценариев модель улавливает, а лучший сценарий не находит; regret@1 в 201 млн руб — это цена ошибки, если довериться её первому месту без OPM-проверки. Внешний цикл верификации (`backend/contexts/optimization/application/verification.py`) для того и написан, но его калибровка на этих числах ещё не проводилась.

**Это числа снятого с эксплуатации checkpoint 18.08.** Именно слабое ранжирование и стало причиной перехода к траекторному ансамблю с отдельной экономической головой. Действующие production-веса на историческом test из 105 сценариев дают Spearman `0.8602`, precision@5 `0.80`, MAE `42.61` млн ₽ (`SURROGATE_DEFENSE.md` §11.1). Сравнивать `0.737` и `0.8602` как «до и после» одного обучения нельзя: это разные архитектуры и разные измеряемые величины (одиночная сеть против бленда 80/20).

**Чего в отчёте нет:** сравнения с CRM на тех же сценариях. Пока `compare_to_baseline` не запущен, гейт задачи 36 не пройден, а числа CRM из §3 сравнению не подлежат — они по объёмам жидкости на одном сценарии.

## 7. Что даёт суррогат и что будет без него

**Формально суррогат необязателен** (`docs/context/06_open_questions.md` §2), но влияет на рейтинг и на решение в спорной ситуации о выходе в финал.

**Без него система работоспособна:** есть CRM как базовая линия, есть правила R0–R7, есть иерархия агентов, есть экономика, сходящаяся с эталонным расчётчиком организаторов до машинного нуля. ЧДД базового сценария на управляемом горизонте 2007–2025 посчитан и защитим — **11 873 122 324.91 ₽** на настоящем прогоне OPM (`20260816T200926-8b4da543d1ed`, витрина `frontend/public/data/npv.json`). Сопоставимый опубликованный результат тНавигатора после переноса с базы 1991 года на 2007 год — **11 903.983 млн руб**; разница симуляторов составляет `−0.259%`.

Важно: существует **второй прогон базы** с ЧДД **11 873 676 459.64 ₽** — те же 224 интервала, отличие `554 134.73 ₽`, это `4.7·10⁻⁵` от величины. Какое из двух чисел произносить — разобрано в `FAQ.md` §11. На этой машине ни один из двух прогонов не лежит; в `data/` есть только `base_run/`.

**С ним появляется** возможность использовать уже реализованные CMA-ES и внешний цикл верификации на настоящих быстрых прогнозах: перебирать тысячи вариантов, отбрасывать OOD-кандидатов и отправлять в OPM только top-k. На 20.08 тракт не был собран: приёмка против CRM технически не собиралась (G8), а precision@1 `0.0` у checkpoint 18.08 означал, что доверять его первому месту без OPM-проверки нельзя. **Сегодня тракт собран** — поиск, физический гейт, сценарный OOD, внешняя OPM-верификация и пакет сдачи описаны в `SURROGATE_DEFENSE.md` §12 и §14. Сравнение с CRM по-прежнему не выполнено: это остаётся открытым пунктом, и заявлять превосходство над CRM мы не имеем права.
