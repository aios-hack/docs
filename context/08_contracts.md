# Контракты данных

Что каждый блок получает на вход и что обязан отдать на выход. Границы, по которым работа режется на независимые куски: контракт зафиксирован — компоненты по обе стороны пишутся параллельно и не ждут друг друга.

Пометки как в `07_concept.md`: **[факт]** — требование или данные организаторов, **[выбор]** — наше инженерное решение, **[гипотеза]** — непроверенная ставка.

Схема потока данных — `README.md`.

---

## 1. Общие правила

### 1.1 Заглушек и моков нет **[выбор]**

Компонент, который не может посчитать, **падает**. `NotImplementedError` законен. `return 0.0`, `return None`, случайный тензор нужной формы — нет.

Причина не стилистическая: ЧДД — одно число, и фальшивое значение, прошедшее через оптимизатор, не детектируется ничем. Расчётный ЧДД организаторов ≠ заявленный → дисквалификация [Онб.14].

Синтетические данные допустимы для проверки формы и конвейера — оси тензоров, сериализация, хеши. В любой метрике качества они запрещены и обязаны быть помечены в метаданных.

### 1.2 Открытые вопросы закрываются политиками, а не заглушками **[выбор]**

Неотвеченный вопрос организаторам становится точкой расширения с **реальными** реализациями по каждой ветке:

| Вопрос | Политика | Ветки |
|---|---|---|
| Налоги в ЧДД (`04_models.md` §6.1) | `TaxPolicy` | с налогами / без |
| Начальный ЭЦН **81 скважины, действующей на t0** (`04_models.md` §6.4) | `InitialEspPolicy` | начисляем в CAPEX / уже установлен |
| Сетка значений (`04_models.md` §6.6) | `QuantizationPolicy` | без квантования / шаг 5 |
| OPEX жидкости, руб/т при объёме в м³ (`04_models.md` §6.3) | `LiquidOpexPolicy` | по объёму / по массе через плотность смеси |

Ответ организаторов переключает флаг, а не переписывает код.

Где реальных реализаций **ноль** — компонента отсутствует в контуре и никем не вызывается. Пример: метрика хрупкости оптимума (`07_concept.md` §8.3).

### 1.3 Производные величины не хранятся **[выбор]**

Всё, что вычисляется из других данных, вычисляется, а не лежит рядом. Типоразмер ЭЦН, стоимости событий, ЧДД в структуре расписания отсутствуют. Два источника истины про одну величину расходятся молча, а эталона для сверки у нас нет.

## 2. Расписание

Структура, из которой генерируется `wells_schedule.inc`, с ней же работают агенты и её показывает UI.

### 2.1 Форма — два слоя событий **[решение, пересмотрено 13.08]**

```
Schedule
  meta:           model=Model_Z, t0=2007-01-01, n_control_dates=225,
                  n_intervals=224, wells[103], provenance, хеши трёх слоёв
  initial_state:  по скважине на t0 — результат replay(префикс с date < t0)
  fixed_deck_events:  [(control_step, well, оператор, сырой аргумент)]
  control_events:     [(control_step, well, kind, value)]
                      kind ∈ SET_LRAT | SET_RATE | OPEN | SHUT | CONVERT_INJ
```

**Слой фиксированных событий обязателен, и это исправление ошибки.** Ранее контракт объявлял генерируемой только часть с режимами фонда, считая перфорации статикой начала дека. Внутри управляющего горизонта лежат 25 блоков `COMPDATMD` (71 запись первичного заканчивания и 48 изменений по действующим скважинам), один `WPIMULT` и ввод 22 скважин (`04_models.md` §3). Всё это данные месторождения, а не решения агента: разрешённые воздействия перечислены в `01_track2_spec.md` §2, ГТМ и дострелы исключены. Расписание, потерявшее этот слой, физически не совпадает с моделью организаторов.

Состояние скважины разложено на четыре независимые величины, иначе ввод не отличается от запуска:

| Поле | Значения |
|---|---|
| `availability` | `NOT_COMMISSIONED` \| `AVAILABLE` |
| `role` | `NONE` \| `PROD` \| `INJ` |
| `operating_status` | `OPEN` \| `SHUT` |
| `setpoint` | м³/сут, применимо при `role ≠ NONE` |

Ось скважин остаётся 103 и во времени не меняется. Скважина, ещё не введённая в работу, присутствует в оси со статусом `NOT_COMMISSIONED`, а не отсутствует.

**Нормализация при `NOT_COMMISSIONED` фиксирована, не произвольна** (найдено при аудите 14.08): `role = NONE`, `operating_status = SHUT`, `setpoint = 0.0`. Без этой фиксации два корректных сериализатора дадут разные байты для одной и той же невведённой скважины, и `canonical_schedule_hash` перестанет быть каноническим.

**Порядок применения внутри шага** — как в деке (`DATES` → `COMPDATMD` → `WCONPROD` → `WCONINJE`, `04_models.md` §3):

1. переход на `control_date[k]`;
2. фиксированные события дека в исходном порядке;
3. управляющие события шага;
4. отклик снимается на следующей дате, если она существует (§2.2).

Плотный вид 103 × 225 получается детерминированной материализацией обоих слоёв и потребляется всем, что ниже.

Почему разреженно: в окне управления режим меняется в 0.85% записей у добывающих и 1.31% у нагнетательных (`04_models.md` §8) — сотни событий против 23 000 чисел. **Счётчиком затрат `len(control_events)` при этом не является** — стоимость определяется переходами состояния (§3.2), а не числом строк.

### 2.2 Горизонт — 225 управляющих дат при 224 интервалах **[решение, принято 13.08]**

Управляемая часть — 01.01.2007 … 09.2025, 225 дат из 371, индекс старта 146 (`04_models.md` §3).

```
control_date[k] = DATES[146 + k]
interval[k]     = [DATES[146 + k], DATES[147 + k])
volume[k]       = cumulative[147 + k] − cumulative[146 + k]
```

Определено для `k = 0 … 223`. Шаг `k = 0` — январь 2007: режим действует на интервал **после** даты, на которую назначен.

**Последняя управляющая дата не имеет интервала.** После блока 01.09.2025 в деке нет следующей `DATES`. Этот шаг несёт семантику `terminal_state`: состояние фонда в нём определено, наблюдаемого отклика и денег — нет. Считать его полным месяцем или молча выбрасывать одинаково запрещено; вопрос о терминальной дате у проверяющей стороны стоит в `06_open_questions.md` §3.12. Если ответ придёт положительный, включается 225-й интервал, и это переключение затрагивает только границу цикла, а не форму типов.

Каждая функция, принимающая индекс, обязана называть шкалу в имени параметра: `control_step` или `deck_step`, никогда просто `step`.

История 1994–2006 в структуру не входит: она свойство модели, а не решения, и не меняется. Хранится как неизменяемый префикс со своим хешем.

`initial_state` — не записанные данные, а результат `replay(history_prefix)` по строгому префиксу `date < t0`: парсер 146 дат до 01.01.2007 отдаёт по каждой скважине доступность, роль, статус и последнюю уставку. Блок 01.01.2007 в префикс **не входит** — он содержит и фиксированные события (первичное заканчивание 12, 17, 110), и управляющие. Рукописная константа здесь запрещена правилом §1.3.

### 2.3 Канонизация и хеш **[выбор]**

События сортируются по `(control_step, well, порядок оператора в шаге)`. Порядок внутри шага семантический, а не алфавитный: фиксированные события дека, затем `CONVERT_INJ`, затем режим и статус. Алфавитная сортировка по `kind` поставила бы `SET_RATE` раньше `CONVERT_INJ` и сменила бы смысл шага.

**Конфликтующие события отклоняются, а не дедуплицируются.** Дедупликация допустима только для точных дубликатов. Два разных `SET_LRAT` одной скважине на одном шаге — ошибка построения расписания, и молчаливый выбор одного из них прячет её.

```
canonical_schedule_hash =
  SHA256( SHA256(canonical_bytes(history_prefix))
        ‖ SHA256(canonical_bytes(fixed_deck_events))
        ‖ SHA256(canonical_bytes(control_events)) )
```

**`+` в прежних формулировках означал конкатенацию 32-байтных дайджестов с последующим SHA-256 поверх, не склейку hex-строк** — hex-конкатенация трёх SHA-256 дала бы 192-символьную строку, а не хеш. `‖` фиксирует это явно: три дайджеста в фиксированном порядке (история, фиксированные события, управляющие), затем ещё один SHA-256, результат — обычные 64 hex-символа, как у любого другого хеша в проекте (§1.6 полной спецификации типов). `canonical_bytes(control_events)` использует порядок из инварианта 1 ниже — не отдельное определение.

**Это единственное имя этой величины во всём проекте, и оно же единственное имя поля везде, где она хранится** — не «хеш дека», не «хеш файла», не `schedule_hash` без уточнения. `RunResult.canonical_schedule_hash` (§4.4) — то же поле, не псевдоним под другим именем. `canonical_schedule_hash` — семантический хеш канонического `Schedule`: не зависит от того, в каком формате (`LosslessTNavEmitter`, `OpmDeckEmitter`, будущий `SubmissionEmitter`) это расписание в итоге записано в файл, и не совпадает с хешем байтов любого из этих файлов (см. `content_hash` в §10.5). Два расписания, эмитированные в разные форматы, но семантически идентичные, обязаны иметь одинаковый `canonical_schedule_hash` и разные `content_hash`.

Все три части входят в ключ кеша. Без хеша префикса подмена дека проходит незамеченной, без хеша фиксированного слоя — потеря перфораций.

### 2.4 Приёмка — два разных round-trip **[решение, принято 13.08]**

Байт-в-байт достижим **только в lossless-режиме парсера**: сохранены сырые токены, пробелы, порядок полей, `1*` и окончания строк. Два семантических слоя сами по себе байтового совпадения не дают, и обещать его без lossless-представления нельзя.

| Проверка | Что сверяется |
|---|---|
| `parse → emit` без изменений | исходный файл воспроизведён байт в байт |
| после правки управления | семантическая сверка: операторы, даты, скважины, значения; фиксированные события совпадают полностью |

Остальная приёмка:

- 103 скважины на выходе `replay`, из них 81 в состоянии `AVAILABLE` и 22 в `NOT_COMMISSIONED` (`04_models.md` §3);
- 30 переводов под закачку воспроизведены в те же даты, 10 из них внутри горизонта;
- фонд и целевые уровни на срезах сходятся с `tools/check_deck_facts.py` (12.2006 — 58 / 23 и 1505 / 1495 м³/сут; 01.2007 — 57 / 27 и 1460 / 1520);
- 25 блоков `COMPDATMD` и `WPIMULT` внутри горизонта присутствуют в выходном файле.

### 2.5 Давление — не рычаг **[выбор]**

Забойные пределы в деке константны: 50 бар на добывающих, 300 на нагнетательных, и это единственные значения во всём файле (`04_models.md` §3). В перечне разрешённых управляющих воздействий давления нет (`01_track2_spec.md` §2).

Следствие: `BHP` в `Schedule` не входит.

При этом онбординг перечисляет давление среди полей выгружаемого управляющего графика [Онб.7]. В сдаваемый `wells_schedule` поле кладём, беря фактическое `WBHP` из отклика финального прогона: требуется поле в выгрузке, а не управляющая ручка.

Если формат требует уставку, а не факт, — вопрос уже стоит в `06_open_questions.md` §3.1.

### 2.6 Не проверено

- Что базовое расписание переэмитится **байт в байт**: зависит от полноты lossless-представления (§2.4). Тогда оракул ослабляется до семантической сверки. **[гипотеза]**
- Обратимость `CONVERT_INJ`. В базе обратных переводов нет — это факт данных, а не доказательство запрета.
- Привязка фиксированных `COMPDATMD`, стоящих на дате базового перевода, если оптимизатор перенесёт перевод на другую дату. Вопрос организаторам — `06_open_questions.md` §3.11.

**Снято 13.08:** пункт про `LRAT = 0` при статусе `OPEN` как бесплатную остановку. Методика начисляет событие по смене состояния действующего фонда (`WLPR > 0` или `WWIR > 0`), поэтому нулевой дебит — это остановка со стоимостью 1.0 млн, а не лазейка (§3.2, `04_models.md` §4).

## 3. Калькулятор ЧДД

### 3.1 Три слоя **[выбор]**

```
ProductionLedger:  IntervalResponse[224] + StateAtDate[371] + Schedule → помесячный реестр
                   {нефть_т, жидкость_м³, закачка_м³, состояние, переходы[]}
EspStateMachine:   StateAtDate[371].liquid_rate   → замены + CAPEX насосов
Economics:         реестр + нормативы + политики → деньги
```

**`StateAtDate` не диагностика — он второй по важности вход в деньги после `IntervalResponse`.** `IntervalResponse` даёт объёмы, из которых считается выручка, OPEX по нефти/жидкости/закачке. Но `StateAtDate.liquid_rate`/`injection_rate` — это то, из чего `ProductionLedger` определяет действующий фонд и переходы состояния (§3.2, по букве Методики — `WLPR > 0 | WWIR > 0`), а значит и содержание фонда, и событийные затраты; и то, из чего `EspStateMachine` подбирает типоразмер и считает CAPEX. Без `StateAtDate` ни состояние, ни ЭЦН не считаются — это деньгообразующий вход не меньше, чем `IntervalResponse`, просто другим путём.

Разделение нужно для раздельной приёмки. Склеенные слои проверяются только целиком, а целиком проверить не с чем.

### 3.2 Состояние и события выводятся из отклика **[решение, пересмотрено 13.08]**

Вход — оба типа отклика (§4.1.1): `IntervalResponse` даёт объёмы (`oil_mass_delta`, `liquid_volume_delta`, `injection_volume_delta`) для денег, `StateAtDate` даёт `liquid_rate`/`injection_rate` для определения состояния фонда и автомата ЭЦН.

Методика определяет состояние и событийные затраты **по факту, а не по расписанию**: *«Скважина относится к действующему фонду, если на расчетном шаге выполняется хотя бы одно условие: `WLPR > 0` или `WWIR > 0`»*, *«Событийные затраты определяются автоматически сравнением текущего состояния скважины с предыдущим расчетным шагом»*.

Ранее контракт утверждал обратное — «события берутся только из `Schedule`, по отклику не отличить `SHUT` от `LRAT = 0`». По Методике различать и не нужно: это одно и то же состояние, и стоит оно одинаково. Проверяющая сторона считает именно так, а расхождение в одном числе означает дисквалификацию.

Автомат состояний:

```
NOT_COMMISSIONED → PROD_ACTIVE | INJ_ACTIVE     ввод, не запуск, 0 руб за событие
PROD_ACTIVE ↔ SHUT                              1.0 млн за переход
INJ_ACTIVE  ↔ SHUT                              1.0 млн за переход
PROD_ACTIVE → INJ_ACTIVE напрямую               5.0 млн + ЭЦН, остановка НЕ начисляется
изменение уставки внутри состояния              0 руб
```

Правила, каждое из которых менялось бы деньгами:

- **смена уставки событием не является** — платят только переходы;
- **непосредственный перевод подавляет остановку.** Это цитата Методики, а не наша трактовка, и политикой с двумя ветками не оформляется;
- **`NOT_COMMISSIONED → ACTIVE` не запуск.** 22 скважины вводятся внутри горизонта (`04_models.md` §3); трактовка ввода как запуска даёт 22 млн лишних расходов и неверный год начисления;
- **содержание фонда 1.0 млн руб/скв·год начисляется только за фактически действующую скважину**, по тому же признаку `WLPR > 0 | WWIR > 0`;
- **первый ЭЦН вводимой скважины подбирается автоматом ЭЦН** по первому фактическому `WLPR` и идёт в CAPEX. Политика начального ЭЦН (§1.2) относится только к 81 скважине, действующей на t0, и на вводимые не распространяется.

`Schedule` остаётся источником намерения, провенанса и валидации, но не источником стоимости. Расхождение «намеревались открыть — фактически не смогла» ловится валидатором (§7.1), а не калькулятором.

**Оси входа и выхода не совпадают, и теперь это видно по типам, а не только по прозе:** `StateAtDate` за все 371 дату, `IntervalResponse` и ЧДД — за 224 интервала управления (§2.2, §4.1.1). Автомат ЭЦН путезависим по `StateAtDate.liquid_rate` и обязан прокрутиться с 1994, иначе типоразмер на 01.01.2007 неверен (`04_models.md` §4). Автомат состояний прокручивается оттуда же: без истории первый шаг управления выглядит как ввод всего фонда разом.

### 3.3 Выход — таблица, не скаляр **[факт]**

Пошаговое и накопленное значение обязательны (`07_concept.md` §5.1.4). Плюс разложение по годам: выручка, отчисления, OPEX по видам, событийные затраты, CAPEX, EBITDA, FCF, `DF`, дисконтированный FCF.

Скаляр на выходе — потеря диагностики: ошибка перестаёт локализоваться.

**Разложение по скважинам обязательно наравне с разложением по годам.** [выбор] Оно определено точно и не требует произвольного распределения затрат: все нормативы Методики скважинного уровня — выручка, OPEX по нефти, жидкости и закачке, содержание действующего фонда, событийные затраты, ЭЦН. Общий на всех только годовой коэффициент дисконтирования. Поскважинные значения суммируются в полный ЧДД без остатка.

Потребители: интерфейс (§12.4), LLM-диагност (§6.1) и дисциплина отключения правил (`07_concept.md` §6).

### 3.4 Дисконт годовой, месячный ряд — его разложение **[решение, принято 13.08]**

Методика агрегирует по календарным годам и дисконтирует годовое: `DF_y = 1/(1+WACC)^(y−y₀)`, y₀ = 2007 (`04_models.md` §4). Своей месячной ставки в калькуляторе нет.

Месячный ряд считается как `FCF_m · DF_{year(m)}` с обязательным тождеством `Σ_{m∈y} = FCF_y · DF_y`.

Замеры, обосновывающие отказ от месячной ставки:

| | Значение |
|---|---|
| Расхождение ЧДД при равномерном FCF | месячный дисконт **на 4.2% ниже** годового |
| Перенос добычи с декабря на январь того же года | месячный: **+9%**, годовой: **ровно 0** |

Второе опаснее первого: месячная ставка платит агенту за перестановки внутри года, за которые настоящая цель не платит, тогда как событийные затраты 1.0 млн и храповик ЭЦН списываются по-настоящему (`04_models.md` §4).

Ряд считается на **224 интервалах**, а не на 225 управляющих датах: терминальный шаг денег не даёт (§2.2). Годовая агрегация от этого не меняется — 2025 год просто заканчивается августовским интервалом.

Следствие для оптимизатора: **γ у RL и `DF` у Методики — разные объекты.** Горизонт конечный, 224 интервала; финансовый дисконт живёт внутри награды, RL-дисконт остаётся отдельным параметром.

Именование обязательное: `npv_methodology` — единственная сдаваемая величина. Никакая другая функция слова `npv` в имени не носит.

### 3.5 Приёмка

Эталонного расчёта организаторы не дали. Два независимых оракула:

- **Порог рентабельности.** Таблица порогов по обводнённости при ρ = 0.9131 и 0.9282 т/м³ посчитана независимо от кода (`04_models.md` §4). Калькулятор обязан воспроизвести все шесть дебитов: 5 → 91.5%, 10 → 95.1%, 20 → 96.9%, 30 → 97.5%, 50 → 98.0%, 100 → 98.3%.
- **Храповик ЭЦН.** `80 → 100 → 125` = 8.65 млн руб, `80 → 125` = 4.55 млн руб (`04_models.md` §4).

Тесты автомата состояний, каждый на одну ошибку:

| Сценарий | Ожидание |
|---|---|
| непосредственный перевод `PROD_ACTIVE → INJ_ACTIVE` | ровно `5.0 млн + ЭЦН`, остановка не начислена |
| смена уставки 10 раз подряд без смены состояния | 0 руб событийных затрат |
| `LRAT = 0` при статусе `OPEN` | остановка, 1.0 млн, содержание фонда за шаг не начислено |
| ввод скважины внутри горизонта | запуск не начислен, ЭЦН подобран по первому `WLPR` |
| **тест размерности:** плотность подана в кг/м³ | расчёт падает или тест ловит расхождение ×1000 (`04_models.md` §4) |

Плюс тождества: сумма месячных = годовое, покомпонентная сходимость `Выручка − Отчисления − OPEX − DR_incl = EBITDA`.

### 3.6 Не проверено

- Помесячная разбивка Методикой **не определена** — она задаёт годовую агрегацию. Месячный ряд целиком наша конструкция.
- Содержание действующего фонда 1.0 млн руб/скв·**год** при неполном годе работы. Пропорционально месяцам — предположение, Методика молчит.
- Входит ли `WEFF` в экономику. В выгрузке трека 1 он есть, в Методике не фигурирует.
- Привязка события к календарному году при переводе под закачку в декабре.

## 4. Мост к симулятору

### 4.1 Три эмиттера, не один **[решение, пересмотрено 14.08]**

**Исправление 14.08.** Один `Emitter` не может одновременно обещать байт-в-байт lossless round-trip и быть входом в OPM: у tNavigator-формата (`COMPDATMD`) и у OPM-формата (`COMPTRAJ`) разный синтаксис заканчивания, а точная спецификация сдаваемого `wells_schedule.inc` организаторами ещё не подтверждена (`06_open_questions.md` §3.1). Склеивать три разные цели в одном компоненте — значит гарантированно нарушить одну из них при правке другой.

```
LosslessTNavEmitter:  Schedule(оба слоя) + prefix     → tNavigator-файл
                       (COMPDATMD, WCONPROD/WCONINJE/DATES как в исходном деке)
OpmDeckEmitter:        Schedule(оба слоя) + Model_Z    → OPM-дек + хеш артефакта
                       (COMPTRAJ вместо COMPDATMD, на тех же 25 датах)
SubmissionEmitter:     Schedule(оба слоя)              → формат организаторов
                       (не реализуется до подтверждения спецификации, §6.2 доп.)
Runner:                OPM-дек + SummarySpec           → RunResult{status, artifacts}
ResponseLoader:        выход OPM                       → StateAtDate[371] + IntervalResponse[224]
```

`LosslessTNavEmitter` — оракул корректности (§2.4): round-trip проверяется на нём, он же используется, пока формат сдачи не подтверждён. `OpmDeckEmitter` — то, что реально исполняется у нас; он **не обязан** быть байт-в-байт совместим с исходным деком, обязан быть физически эквивалентен. `SubmissionEmitter` — заглушка задачи, а не компонент: реальной реализации нет, пока нет ответа организаторов (правило §1.2, ветка «формат не подтверждён»).

**`ResponseLoader` считает приросты строго внутри скважины и разводит две шкалы в два типа**, а не в один тензор с плавающим выравниванием — на этом уже спотыкались (§4.1.1). Требования к приростам: сортировка `(well, deck_step)`, разность внутри скважины, снятая терминальная строка, обязательный тест границы скважин (`04_models.md` §5).

### 4.1.1 `StateAtDate` и `IntervalResponse` — раздельные типы, не один тензор **[решение, принято 14.08]**

**Исправление 14.08.** Прежняя форма — один массив `371×103×каналы`, куда мгновенные величины (`WLPR`, `WWIR`, `WBHP`) и помесячные приросты (`WOMT_Diff`, `WLPT_Diff`, `WWIT_Diff`) складывались в один тензор с общим индексом. Это создавало ровно ту ошибку выравнивания, которую правило §2.2 обязано было предотвратить: снятие «терминальной строки» при подсчёте приростов (forward align, `delta[i]` живёт на строке `i`) и формула `volume[k] = cum[147+k] − cum[146+k]` (backward align, значение живёт на строке `147+k`) в одном типе противоречат друг другу. Развожу в два типа с разными осями и разной семантикой индекса — тогда противоречить нечему.

```
StateAtDate[371]:                         ось — 371 дата дека, включая индекс
  deck_date_index, well                   0…370; мгновенные величины на дату
  liquid_rate        м³/сут                WLPR на эту дату
  injection_rate     м³/сут                WWIR на эту дату
  bhp                бар                   WBHP на эту дату
  active_control_mode перечисление         RATE_TARGET | BHP_LIMITED | SHUT |
                                            NOT_COMMISSIONED | UNKNOWN (§4.3)

IntervalResponse[224]:                    ось — 224 подтверждённых интервала (§2.2)
  control_step, well                      0…223, интервал [DATES[146+k], DATES[147+k])
  oil_mass_delta       т                  cum(WOMT)[147+k] − cum(WOMT)[146+k]
  liquid_volume_delta  м³                 cum(WLPT)[147+k] − cum(WLPT)[146+k]
  injection_volume_delta м³               cum(WWIT)[147+k] − cum(WWIT)[146+k]
```

Никакой строки `147` или `146` за пределами этого типа не существует: `deck_date_index` живёт только в `StateAtDate`, `control_step` — только в `IntervalResponse`, и они разного размера (371 против 224) — перепутать оси невозможно на уровне типов, а не только по соглашению в прозе.

**Вычисление `IntervalResponse` — два шага, порядок обязателен**, иначе воспроизводится прежняя ошибка выравнивания:

```
1. raw_diff[i] = cumulative[i+1] − cumulative[i]     i = 0…369, строго внутри (well,)
                 терминальная строка i=370 не имеет i+1, в raw_diff не входит — здесь и только
                 здесь «снимается терминальная строка» (§4.1)
2. IntervalResponse[k] = raw_diff[146 + k]            k = 0…223, простая переиндексация
```

Обратный порядок — сначала спроецировать на 224 интервала, потом решать, какую строку «снять», — источник прежнего противоречия: `IntervalResponse` не хранит `deck_date_index` нигде, эта ось существует только внутри шага 1.

**Исправление 14.08: `StateAtDate` не диагностический тип, а второй деньгообразующий вход.** Через него Методика определяет действующий фонд и переходы состояния (`WLPR > 0 | WWIR > 0`, §3.2), а значит — содержание фонда 1.0 млн руб/скв·год, событийные затраты, и через `EspStateMachine` — типоразмер и CAPEX насоса. `bhp`/`active_control_mode` — диагностические и валидационные, эти два поля действительно не входят в деньги напрямую. Смешивать «`StateAtDate` не входит в деньги» и «`bhp`/`active_control_mode` не входят в деньги» было ошибкой прежней формулировки.

`StateAtDate` нужен: автомату ЭЦН (путезависим по `liquid_rate`, требует все 371), автомату состояний `ProductionLedger` (§3.2), динамическому валидатору (§7.1, `факт/цель` и режим контроля), диагностике недостижимости.

`IntervalResponse` нужен: калькулятору ЧДД как источник выручки и OPEX по объёму (§3.2 — Методика считает по месячным объёмам, не по мгновенным дебитам), суррогату как первичный целевой выход по деньгообразующим каналам (§5.1).

**Обводнённость и типоразмер ЭЦН остаются производными** — выводятся из обоих типов вместе (`1 − (oil_mass_delta/ρ) / liquid_volume_delta`, ЭЦН — из траектории `liquid_rate` в `StateAtDate`), двух источников истины не заводим.

### 4.1.2 Join двух типов — тройка, которую использует каждый денежный потребитель **[выбор]**

Разные типы с разными осями не отменяют off-by-one у потребителя, который читает оба сразу: `ProductionLedger`, автомат состояний, `EspStateMachine`, `Economics` — все читают **текущее и предыдущее** состояние на каждом интервале, чтобы увидеть переход. Фиксирую join явно, одной тройкой, а не оставляю каждому потребителю выводить его самостоятельно:

```
для k = 0…223:
  response[k]        = IntervalResponse[k]
  current_state[k]    = StateAtDate[147 + k]
  previous_state[k]   = StateAtDate[146 + k]
```

`current_state[k]` — состояние **на конец** интервала `k` (дата `DATES[147+k]`), `previous_state[k]` — на его начало (дата `DATES[146+k]`, совпадает с `current_state[k-1]` для `k ≥ 1`; при `k=0` это `StateAtDate[146]`, последняя историческая дата перед управлением). Переход состояния между `previous_state[k]` и `current_state[k]` — то, что стоит денег (§3.2).

**Приёмочный тест обязателен на трёх точках:** `k=0` (стык истории и управления, `previous_state[0] = StateAtDate[146]`), произвольный `k` из середины (например `k=112`), и `k=223` (последний подтверждённый интервал, `current_state[223] = StateAtDate[370]` — последняя дата дека). Тест на этих трёх точках ловит off-by-one, который тест только на «типичном» `k` не поймает.

### 4.2 Дек делится на неизменяемое и генерируемое, конверсия — не разовая **[решение, пересмотрено 14.08]**

Статика: сетка, свойства, `init`, `regs`, сконвертированный начальный блок `WELTRAJ` (103 траектории, до первой `DATES`). Расписание генерируется целиком, включая слой фиксированных событий дека (§2.1), `.DATA` собирается через `INCLUDE`.

**Конверсия `COMPDATMD → COMPTRAJ` не однократна.** Прежняя формулировка предполагала разовое преобразование в начале дека. После §2.1 фиксированный слой содержит 25 блоков `COMPDATMD` внутри горизонта управления, на 25 разных датах (`04_models.md` §3) — `OpmDeckEmitter` обязан конвертировать каждый из них на его собственной дате, а не только начальные 103 траектории. Задача 2 и её приёмка (§4.7) пересмотрены под это.

Конверсия геометрии — единственная по-настоящему рискованная часть (`04_models.md` §1.1), пересобирать её на каждом прогоне нельзя. Выполняется кодом, не руками: Docker-образ обязан быть воспроизводим [Онб.14].

### 4.3 `SummarySpec` — часть контракта **[выбор]**

Секция SUMMARY в деке пустая, 4 строки (`04_models.md` §1.1) — состав пишем мы. Спецификация объявляется один раз, хешируется и входит в ключ кеша: добавленный ключ меняет форму `StateAtDate`/`IntervalResponse` у всех потребителей.

Обязательные ключи: `WOMT`, `WLPT`, `WWIT`, `WLPR`, `WWIR`, `WBHP` — потребляет Методика и оба типа отклика. Плюс `WMCTL` (режим контроля скважины), если OPM его отдаёт — проверяется на задаче 3, статус пока §4.8.

**Домен `active_control_mode` — пять значений, не два** (исправлено 14.08, было `RATE_TARGET | BHP_LIMITED` — не покрывало неактивную скважину и неопределённость симулятора):

```
RATE_TARGET        цель по дебиту/закачке активна и близко достигнута
BHP_LIMITED         скважина упёрлась в предел 50/300 бар, цель недостигнута
SHUT                скважина активна (AVAILABLE), но остановлена на эту дату
NOT_COMMISSIONED     скважина ещё не введена в работу (Schedule.availability)
UNKNOWN              WMCTL недоступен/не распознан, и правило вывода неприменимо
```

Отображение `WMCTL → active_control_mode` — прямое там, где `WMCTL` определён; при отсутствующем или нераспознанном значении ключа — `UNKNOWN`, не молчаливый выбор одного из содержательных значений.

Если `WMCTL` недоступен, для активной скважины (`Schedule.availability = AVAILABLE`, `operating_status = OPEN`) с положительной уставкой правило вывода: `BHP_LIMITED`, когда `факт/цель < 0.999` **и** `bhp` в пределах допуска от 50/300 бар; иначе `RATE_TARGET`. **Fallback по `факт/цель` запрещён вне этого условия**: для `SHUT` и `NOT_COMMISSIONED` цель нулевая или отсутствует, деление и любая классификация через `факт/цель` не производятся — состояние берётся напрямую из `Schedule`. Явное поле из симулятора приоритетнее выведенного правила везде, где оно распознано.

### 4.4 Падение прогона — данные, а не исключение **[выбор]**

`RunResult.status ∈ {OK, NOT_CONVERGED, FAILED}`, наружу не бросается.

Генератор датасета делает сотни прогонов, часть развалится, и датасет обязан помнить какие: несошедшийся прогон — сигнал, что расписание физически невозможно.

### 4.5 Кеш и параллельность **[выбор]**

Ключ: `hash(deck_artifact) + canonical_schedule_hash + hash(summary_spec)`. Попадание экономит полный прогон.

Рабочая директория на прогон, общего состояния нет.

### 4.6 Эмит полный, не разреженный **[выбор]**

Базовый дек пишет `WCONPROD` на каждом из 371 шага. `LosslessTNavEmitter` воспроизводит его байт в байт в lossless-режиме, а это наш единственный оракул (§2.4). Разреженный вариант — флаг, не умолчание.

**Фиксированные события дека не теряются ни в одном из трёх эмиттеров.** 25 блоков `COMPDATMD`, `WPIMULT` и ввод 22 скважин внутри горизонта переносятся в выходной файл в исходном порядке шага (§2.1) — в `LosslessTNavEmitter` как есть, в `OpmDeckEmitter` как `COMPTRAJ` на тех же датах (§4.2). Расписание без них описывает другое месторождение, и проверить это по числу ЧДД невозможно — оно просто будет другим.

### 4.7 Приёмка

Структурные (`04_models.md` §1.1), для `OpmDeckEmitter`: 103 скважины на входе и выходе, суммарная вскрытая длина сохранена, каждая скважина в том же пласте по `Model_Z_regs.inc`, координаты голов совпадают с первыми точками `WELLTRACK`.

**Сохранность фиксированного слоя проверяется в обоих форматах, не только в lossless.** В `LosslessTNavEmitter` — те же 25 блоков `COMPDATMD` с теми же датами и записями, тот же `WPIMULT` на 01.05.2025. В `OpmDeckEmitter` — те же 25 дат несут `COMPTRAJ` с эквивалентной геометрией (§4.2), а не только начальные 103 траектории. Пропуск любого из 25 внутригоризонтных блоков в OPM-деке — брак конверсии, даже если lossless-файл прошёл проверку: это два независимых компонента, и прохождение одного не свидетельствует о другом.

Физические на базовом прогоне — диагностика конверсии, не жёсткий отбраковывающий oracle: обводнённость по фонду **как правило** растёт на длинном горизонте без резких провалов, пластовое давление не улетает, материальный баланс сходится с поправкой на аквифер, 30 переводов под закачку меняют роль в нужные даты. **Исправление 14.08:** строгая помесячная монотонность не требуется — локальные колебания из-за ввода/вывода скважин и перераспределения потоков физически возможны; устойчивое долгосрочное падение или разрыв материального баланса — это сигнал брака конверсии, разбирается человеком, а не бинарный gate.

### 4.8 Не проверено

- Отдаёт ли OPM массовые ключи `WOMT` / `WOMR`. Если нет — плотность применяем сами, и контракт отклика меняется.
- Что OPM проглотит `WELTRAJ` / `COMPTRAJ` на нашем деке. Проверено чтением исходников `opm-common`, прогонов ноль (`04_models.md` §1.1).
- Поддержка `LGR`, `AQUDIMS` (аквифер 2778 ячеек), `ENDSCALE`.
- Средние поля `COMPDATMD` у tNavigator (`04_models.md` §1.1). Перенос не в те колонки даёт тихо неверную конверсию.
- **Время прогона OPM неизвестно.** 15 минут — замер по tNavigator [12.08 35:18]. На 547 638 ячейках с аквифером OPM может дать существенно больше. Число доступных прогонов определяет, какая архитектура суррогата нам доступна (`07_concept.md` §5.3).

## 5. Суррогат

Контракт фиксируется, хотя семейство модели остаётся открытым (`07_concept.md` §8.1): вход и выход от внутреннего устройства не зависят.

### 5.1 Выход — интервальные объёмы и мгновенные состояния, оба деньгообразующие **[решение, пересмотрено 14.08]**

**Исправление 14.08.** Прежняя формулировка выдавала только мгновенные `liquid_rate`/`injection_rate` и оставляла открытым, как из них получить помесячный объём для Методики. Умножение дебита на число дней интервала — приближение: реальный `WLPR`, который отдаёт OPM, есть отчётное значение на конец шага, а не средний по интервалу расход, и при негладком режиме эти две вещи расходятся. Раз калькулятор ЧДД считает по объёмам (§3.2), а не по дебитам, **суррогат обязан целиться в объём напрямую**, а не в дебит с последующим домножением.

```
IntervalResponse[224]  (§4.1.1, деньгообразующий выход):
  oil_mass_delta          т     цель обучения — то, что напрямую входит в выручку
  liquid_volume_delta     м³    цель обучения
  injection_volume_delta  м³    цель обучения

StateAtDate[371]  (второй деньгообразующий выход, только 147…370 предсказывается):
  liquid_rate      м³/сут   фактический WLPR на конец интервала, не цель
  injection_rate   м³/сут   фактический WWIR на конец интервала, не цель
  bhp              бар      диагностика, не входит в деньги напрямую
  active_control_mode       диагностика; RATE_TARGET | BHP_LIMITED | SHUT |
                             NOT_COMMISSIONED | UNKNOWN (§4.3)
```

**`liquid_rate`/`injection_rate` не запасной, а обязательный supervised target, и он влияет на деньги, просто не через выручку.** Через них `ProductionLedger` определяет действующий фонд и переходы состояния (§3.2, §4.1.2), а `EspStateMachine` — типоразмер и CAPEX. Ошибка в предсказанном `liquid_rate` рядом с нулём (пропущена остановка/запуск, не увидено пересечение порога ЭЦН) стоит денег так же реально, как ошибка в объёме, просто по другому счёту Методики. `oil_mass_delta` и `liquid_volume_delta` предсказываются как отдельная, первичная цель для выручки — а не выводятся из `liquid_rate × дни_интервала` — но это не делает `liquid_rate` второстепенным: `bhp` и `active_control_mode` — вот что действительно только диагностика и валидация, не деньги. Если модель по архитектуре хочет предсказывать дебит и объём одной головой — обязана штрафоваться на согласованность обоих выходов; метрики приёмки на оба выхода раздельны (§5.5).

**Достижимость цели каналом не является — она производная:** `факт / цель` считается потребителем из уставки расписания и предсказанного факта (по `liquid_volume_delta` или по `liquid_rate`, в зависимости от того, что сравнивается — накопленное или мгновенное). Требование §5.1.1 концепции сохраняется: модель обязана предсказывать факт, расходящийся с целью, просто выражается это непрерывной величиной, а не флагом.

`BHP` и `active_control_mode` нужны, чтобы объяснить недостижимость и проверить физическую правдоподобность — предел 50 бар на добывающих, 300 на нагнетательных, единственные значения во всём деке (`04_models.md` §3).

**Оси согласованы явно, теперь по типам §4.1.1, а не по прозе:**

| | Диапазон |
|---|---|
| Прогноз суррогата, `IntervalResponse` | все 224 интервала, `control_step = 0…223` |
| Прогноз суррогата, `StateAtDate` | даты дека 147…370 (соответствуют `control_step` 0…223) |
| Историческая часть, `StateAtDate` | даты дека 0…146, из базового прогона, не предсказывается |

История одна и та же во всех сценариях (начальное состояние пласта и префикс расписания фиксированы), поэтому склейка `StateAtDate` для автомата ЭЦН детерминирована и не требует прогона на каждый кандидат.

**Жёсткое требование:** выход суррогата — `IntervalResponse` и `StateAtDate` тех же форм, что выдаёт `ResponseLoader` (§4.1.1). Иначе калькулятор ЧДД не примет обе ветви и система распадается на две несвязанные.

### 5.2 Детектор выхода за обучающий диапазон — часть выхода **[факт]**

Возвращается вместе с прогнозом, всегда, не опцией. Организаторы назвали его критерием масштабируемости [10.08 35:40].

### 5.3 Вход — только целевые накопления **[решение, принято 13.08]**

`SurrogateInput` выводится из одного `Schedule` — обоих его слоёв — плюс статика скважины и измеренная λ своего окна (§8.1.1). Ни одного числа от симулятора.

Накопления считаются **с 1994**, а не с 2007: по всем сценариям это одинаковая добавка, но не ноль — скважина после 13 лет заводнения не равна себе же в начале.

Доступность скважины — обязательный признак: 22 скважины вводятся внутри горизонта, и до своей даты у них нет ни накоплений, ни соседства, а нулевой дебит означает «ещё не существует», а не «остановлена» (`04_models.md` §3).

Обоснование: начальное состояние пласта фиксировано, история у всех сценариев одна. Значит фактические накопления — детерминированная функция от траектории управления, и информация не теряется, а перекладывается на модель.

Что это разрешает: §5.1.2 концепции требует накопленные признаки, §5.1.4 запрещает прокрутку. Фактическая накопленная добыча на шаге `t` — это то, что мы предсказываем, и без прокрутки её на входе нет. Целевые накопления известны заранее из расписания и конфликта не создают.

Следствия:
- фичеризатор пишется и тестируется без работающего OPM;
- датасет вырождается в тройки `(Schedule, StateAtDate, IntervalResponse)`, выравнивать нечего;
- утверждение «задача почти марковская» (`07_concept.md` §5.1.2) ослабевает — состояние не сжимается в короткий вектор, может понадобиться длинное окно по истории управления. **[гипотеза]**

### 5.4 Требование к плану возмущений **[выбор]**

Целевая закачка расходится с фактической тем сильнее, чем агрессивнее режим, — то есть признак систематически врёт ровно там, куда полезет оптимизатор.

**В план возмущений обязаны входить заведомо недостижимые уставки.** Без них модель выучит тождество «цель = факт» — ту самую ловушку, от которой защищается `07_concept.md` §5.1.1.

### 5.5 Метрика и приёмка **[факт]**

Ранговая корреляция по ЧДД, не MAE, плюс отдельная метрика по обводнённости (`07_concept.md` §5.2).

Базовая линия — CRM. Любая модель обязана бить его по ранговой корреляции, иначе отвергается (`07_concept.md` §5.1.3).

**Одной ранговой корреляции по ЧДД и метрики по обводнённости недостаточно** — они не видят ошибок `StateAtDate`, а тот денег стоит не меньше `IntervalResponse` (§5.1). Обязательные дополнительные метрики приёмки:

| Метрика | Что ловит |
|---|---|
| Точность `ACTIVE`/`SHUT` по `liquid_rate`/`injection_rate` против порога Методики | суррогат путает «работает» и «остановлена» — это 1.0 млн за ложный переход |
| Точность переходов состояния (§3.2) | ложные `PROD_ACTIVE ↔ SHUT`, ложный ввод/перевод |
| Ошибка на порогах выбора типоразмера ЭЦН | суррогат промахивается мимо границы интервала — CAPEX 0.55…8.05 млн руб |
| Ошибка событийных затрат и CAPEX ЭЦН, посчитанных по предсказанному `StateAtDate` против факта | сводная денежная ошибка второго входа, а не только первого |
| Accuracy/F1 по `active_control_mode = BHP_LIMITED` | суррогат не видит недостижимость — прямая причина ловушки §5.1.1 концепции |
| Ошибка `bhp` | физическая правдоподобность (§7.1) |

Физические проверки — диагностика, не жёсткий отбраковывающий oracle: обводнённость **обычно** не падает при росте закачки, материальный баланс не нарушается. **Исправление 14.08:** монотонность обводнённости нельзя требовать как строгий инвариант — лаг отклика, ввод и вывод скважин, перераспределение потоков между соседями способны дать физически корректное локальное падение. Нарушение логируется и разбирается человеком, а не автоматически отбраковывает прогноз.

### 5.6 Не проверено

- Сколько прогонов реально получим — не замерено, а это определяет доступную архитектуру.
- Устойчивость λ между независимыми партиями прогонов и её дрейф во времени (`07_concept.md` §6).
- Что `oil_mass_delta`/`liquid_volume_delta` прилично предсказуемы вблизи ограничения по забойному давлению: там `liquid_rate` ведёт себя почти разрывно, и объём внутри интервала может отражать смесь режимов. **[гипотеза]**
- Как модель ведёт себя на шагах ввода 22 скважин: состав действующего фонда меняется не по управлению, и в признаках это должно быть видно (§5.3).
- Точность приближения «объём предсказан напрямую» против «дебит × дни»: замер расхождения на базовом сценарии, где обе величины известны из OPM, — сделать до того, как выбрана архитектура суррогата.

## 6. МАС и оптимизатор

Контракт фиксируется, хотя семейство оптимизатора остаётся открытым (`07_concept.md` §8.2).

### 6.1 Две границы **[выбор]**

```
Policy:     FieldState + Constraints + Groups + θ  → Schedule + Trace
Optimizer:  θ → {objective, feasible, violations_by_scenario, provenance}
```

Оптимизатор по-прежнему слеп к скважинам: двигает ≤10 чисел и не знает ни фонда, ни расписания. Но **скаляра на выходе недостаточно**: устойчивость сформулирована как ограничение, а не штраф (§13.3), и скалярная форма заставила бы исполнителя самому придумать, как зашить ограничение в одно число — то есть ввести штраф, запрещённый двумя разделами ниже.

| Поле | Смысл |
|---|---|
| `objective` | ЧДД по Методике на номинальном сценарии |
| `feasible` | выполнены ли ограничения батареи и `Constraints` |
| `violations_by_scenario` | по каждому сценарию: величина просадки и что именно нарушено |
| `provenance` | хеши суррогата, `Groups`, датасета, seed |

Замена CMA-ES на градиент по дифференцируемому суррогату или на обученную политику не задевает ничего вокруг: меняется способ двигать θ, не форма ответа.

Три уровня иерархии (`07_concept.md` §6) и есть эта параметризация: менеджер раздаёт лимиты по группам, агент участка распределяет внутри лимита, исполнитель валидирует физические ограничения и квантует.

### 6.2 `Groups` — версионированный артефакт **[выбор]**, алгоритм — **[гипотеза]**

Считается из измеренной матрицы влияния λ один раз (`07_concept.md` §6), в θ не входит. Имеет собственный хеш и участвует в ключе кеша наравне с деком: пересчитали λ — сменился хеш — старые результаты не смешались с новыми.

**Контрактом является форма артефакта, а не способ его получения.** Алгоритма нет: `Groups = f(λ)` — это имя задачи, а не спецификация. До того, как λ измерена, не определены ни направленность графа (λ несимметрична: влияние нагнетательной на добывающую), ни число групп, ни допустимость перекрытий, ни принадлежность переведённых скважин, побывавших в обеих ролях.

Фиксируется только то, что можно проверить без данных:

| Требование | Проверка |
|---|---|
| детерминированность при том же λ и seed | двойной прогон даёт одинаковый хеш |
| каждая скважина принадлежит хотя бы одной группе | покрытие 103 из 103 |
| группа непуста и содержит хотя бы одну нагнетательную | иначе управлять закачкой внутри группы нечем |
| разбиение переживает пересчёт λ на второй партии прогонов | доля переехавших скважин возвращается вместе с артефактом |

Выбор алгоритма — задача 61, делается после задачи 28 и на её данных. До этого момента «нарезка из измеренной λ» остаётся гипотезой, а не решением, и на защите формулируется так же.

### 6.3 `Constraints` — первоклассный вход **[факт]**

Тестовый кейс приходит именно в этих терминах: ограничение по воде в конкретном году, выпадение скважин, нижняя граница добычи [12.08 24:25]. Возмущения даются заранее, в описании кейса, а не подкидываются посреди прогона (`07_concept.md` §5.1.4).

Декларативный объект: лимиты по закачке по годам, окна недоступности скважин, нижние границы добычи.

**Сериализуемый документ, который интерфейс порождает, а не только читает** [Онб.12]: UI обязан позволять задавать ограничения и сценарии.

### 6.4 `Trace` обязателен **[выбор]**

По каждой скважине-месяцу: какое правило сработало и с какими числами.

Без трассы объяснимость, которая по концепции достаётся даром (`07_concept.md` §6), не достаётся вообще, а дисциплина против разрастания набора правил (там же) ничем не измеряется. Отсюда же требование: каждое правило R0–R7 включается и выключается флагом — это часть контракта, а не отладочная возможность.

### 6.5 Разрешение состояния — неподвижная точка **[решение, принято 13.08]**

Правила читают **фактическое** состояние: R0 нужен дебит и обводнённость, R2 обводнённость, R3 месяцы убытка, R5 фактическая компенсация. Суррогат при этом оценивает траекторию целиком, прокрутки нет (`07_concept.md` §5.1.4) — политике неоткуда взять состояние на шаге `t`.

Дисциплина «только целевые накопления» (§5.3) здесь неприменима: правила по определению про факт, и в этом их ценность.

Схема при фиксированном θ:

```
Schedule₀ = policy(initial state)
повторять:  (StateAtDate_k, IntervalResponse_k) = surrogate(Schedule_k)
            Schedule_k+1                        = policy(состояние из StateAtDate_k)
до          canonical_schedule_hash(Schedule_k+1) == canonical_schedule_hash(Schedule_k)
            либо потолок итераций
```

Контракт суррогата не затрагивается — он по-прежнему получает расписание целиком. Цена: несколько прогонов суррогата на кандидата вместо одного, при стоимости прогона в доли секунды.

Проверка сходимости бесплатна: расписание канонизировано и хешируется (§2.3), совпадение хешей и есть неподвижная точка.

Расходимость — не исключение, а исход. Результат несёт `converged: bool` и число итераций.

**При упоре в потолок «лучший посещённый» берётся только после финальной переоценки.** Расписание `Schedule_k+1` построено политикой по отклику на `Schedule_k`, то есть его `Trace` объясняет состояние другого расписания, а динамические ограничения могли проверяться не на нём. Поэтому выбранный кандидат обязательно прогоняется через суррогат ещё раз, и результат несёт:

```
self_consistent: bool     совпадает ли отклик, по которому принимались решения,
                          с откликом на само выбранное расписание
```

Несамосогласованный кандидат допустим как результат, но помечен: ЧДД, `Trace` и нарушения берутся с финальной переоценки, а не с итерации, на которой он родился. Тот же порядок действует после внешнего цикла верификации (§10).

### 6.6 Не проверено

- **Сходимость не доказана.** R3 с гистерезисом и R7 с цикликой дискретны, между итерациями возможны автоколебания. Частота расходимости замеряется флагом `converged`. **[гипотеза]**
- Найденное расписание — неподвижная точка пары «политика ∘ суррогат», а не «политика ∘ физика». На корректность это не влияет, на качество влияет; на защите формулировать точно.
- Хватает ли 10 параметров. Потолок признан честным в `07_concept.md` §6, замера нет.
- Качество LLM-диагноста автоматически не проверяется, оценивается человеком [10.08 10:04].

**Снято 14.08:** пункт «метрики хрупкости оптимума нет» был устаревшим и противоречил §13, где метрика (regret по батарее сценариев, ограничение а не штраф) зафиксирована с 13.08. Найдено при повторной вычитке 14.08 — живое противоречие, не только в историческом журнале.

## 7. Валидатор режимов

Требование организаторов: в сдаваемом расписании **отсутствуют физически невозможные режимы** [10.08 24:28].

### 7.1 Проверка двухфазная **[выбор]**

```
validate_static(Schedule)                                → [нарушения]   # до эмита
validate_dynamic(StateAtDate, IntervalResponse)            → [нарушения]   # после прогона
```

Статическая фаза проверяет то, что видно из расписания: уставки в допустимом диапазоне, тип события соответствует текущей роли скважины, `SET_LRAT` не адресован нагнетательной, `CONVERT_INJ` не повторяется, события лежат внутри 225 шагов, управляющее событие не адресовано скважине в состоянии `NOT_COMMISSIONED`, **управляющее событие не адресовано `control_step = 224`** (терминальный шаг без интервала, §2.2 — нет смысла назначать режим на месяц, которого не будет), фиксированный слой дека не изменён, ограничения из `Constraints`, выразимые в уставках, соблюдены.

Динамическая фаза проверяет то, что видно только по отклику (`StateAtDate`/`IntervalResponse`, §4.1.1):

| Проверка | Почему статикой не закрывается |
|---|---|
| `факт / цель` по добыче и по закачке — только для активных скважин с положительной уставкой (§4.3) | недобор цели из расписания не выводится; для `SHUT`/`NOT_COMMISSIONED` цель нулевая или отсутствует, деление не производится |
| `active_control_mode` (все пять значений, §4.3) | режим определяет симулятор, а не мы |
| забойное давление в пределах 50 / 300 бар | из расписания не выводится |
| нижние границы добычи нефти из `Constraints` | зависят от факта |
| верхние пределы по жидкости и закачке | зависят от факта |
| предел по обводнённости | обводнённость производна от отклика |
| инфраструктурные лимиты | суммарные величины по факту |

**Проверка одних только пределов `BHP` почти вырождена.** Симулятор сам переключится на ограничение по давлению и предел не нарушит — вместо нарушения он молча недоберёт целевой дебит. Валидатор, смотрящий только на `BHP`, всегда доволен, а расписание при этом не выполнено. Ловит это отношение `факт / цель` вместе с активным режимом контроля; они же дают причину недостижимости, которую видит человек в интерфейсе.

**Считать, что статическая фаза закрыла требование организаторов, — ошибка.** Ни `BHP`, ни факт из расписания не выводятся.

### 7.2 Вызывается всегда **[выбор]**

Гейт перед эмитом, независимо от происхождения расписания: политика, гибридная поправка на десяток скважин (`07_concept.md` §6) или ручная правка из интерфейса. Поправка применяется **после** политики и способна нарушить то, что политика соблюдала.

Возвращает список нарушений, а не булево значение: нарушение должно быть предъявимо человеку и попадать в интерфейс.

## 8. Измерение связности

`Groups` (§6.2) принимает λ как данность. Здесь — кто её производит.

### 8.1 Два компонента **[выбор]**

```
DoEPlanner:       базовое расписание + активные нагнетательные окна
                                                       → возмущённые расписания
LambdaEstimator:  {расписание, отклик} + матрица плана  → λ[окно] + лаг + устойчивость
```

План Плакетта-Бермана: половина нагнетательных на повышенный режим, половина на пониженный по матрице плана; главные линейные эффекты разделяются за число прогонов порядка числа скважин плюс запас (`07_concept.md` §5.1.3).

### 8.1.1 λ оконная, размер плана задаётся датой **[решение, принято 13.08]**

**41 нагнетательной в раннем окне не существует.** 41 — это число скважин, побывавших нагнетательными за весь горизонт. На 01.01.2007 их 27, к 2012 — 37, 41 набирается только к 2022 (`04_models.md` §8). План на 41 скважину в начале управления потребовал бы досрочно перевести 14 добывающих, то есть измерять другой объект — фонд, которого в этот момент нет.

Отсюда:

- план строится на **активном фонде нагнетательных на дату начала окна**, и его ширина — свойство окна, а не константа;
- `Lambda` несёт временную область применимости: дата начала и конца окна, список нагнетательных и добывающих, для которых оценка получена;
- скважины, введённые или переведённые внутри окна, в матрицу этого окна не входят и оцениваются в следующем;
- потребители (`Groups`, признак суррогата, правило R1, главный вид интерфейса) обязаны знать, к какому окну относится матрица, которую они читают.

Дрейф λ во времени (`07_concept.md` §8.4) из отдельного вопроса становится следствием этой формы: несколько окон дают несколько матриц, сравнение которых и есть замер дрейфа.

### 8.2 Правила оценки **[выбор]**

Иначе каждая реализация выберет своё и результаты не сравнятся:

- отклик считается **не по мгновенному дебиту, а по накопленной добыче в окне** после воздействия (`07_concept.md` §5.1.3);
- лаг подбирается перебором по сетке, выбирается максимизирующий `R²` регрессии;
- **регрессия идёт на фактические `ΔWWIR`, а не на проектные уровни плана.** Скважина, не добравшая целевую закачку, не выбрасывается из плана: её колонка заполняется тем, что реально произошло;
- вместе с оценками возвращаются **ранг и число обусловленности** матрицы фактических воздействий. Ортогональность плана — свойство замысла; после столкновения с пределом 300 бар она проверяется, а не предполагается;
- достижимость (`achievability_ok`) остаётся диагностикой: она объясняет плохую обусловленность, но сама по себе не является критерием исключения скважины;
- устойчивость меряется двумя независимыми партиями плана и возвращается вместе с λ, а не проверяется постфактум.

**λ — коэффициенты чувствительности, а не доли аллокации.** Размерность у них есть: приращение накопленной добычи соседа на единицу приращения закачки. Ограничение «сумма долей не больше единицы» к ним неприменимо — оно относится к безразмерным долям CRM. Материальный баланс как ограничение остаётся, но накладывается на потоки в суррогате, а не на строки матрицы (`07_concept.md` §5.1.3).

Результат — версионированный артефакт с хешем, входит в ключ кеша наравне с деком.

### 8.3 Амплитуда возмущения — протокол, а не выбор **[решение, принято 13.08]**

Ограничение сверху — не шум, а **нелинейность**: λ имеет смысл, пока отклик приблизительно пропорционален воздействию. Величина назначаться не может, она замеряется.

```
3–4 нагнетательные с разной плотностью окружения × амплитуды {5, 10, 20, 40}%
отношение накопленного отклика соседей к амплитуде → точка, где перестаёт быть постоянным
рабочая амплитуда = половина от точки излома
```

Порядка 12–16 прогонов против ~96 при лобовом «прогнать весь план на двух амплитудах».

**Вторая граница жёстче первой: достижимость.** Нагнетательные ограничены 300 бар (`04_models.md` §3). Если при верхнем уровне скважина не добирает целевую закачку, план спроектирован на одни уровни, а реализовались другие — **матрица плана перестаёт быть ортогональной, и все оценки λ плывут разом**. Асимметрия усугубляет: снижение закачки достижимо всегда, повышение — нет.

Отсюда обязательная проверка после каждого возмущённого прогона: фактическая приёмистость против целевой. Недобор — не повод выбрасывать скважину: регрессия всё равно идёт на фактические `ΔWWIR` (§8.2), а недобор виден в числе обусловленности. Систематический недобор на верхнем уровне означает, что общая амплитуда завышена, и роняет её для всего плана.

**Приор, доступный без прогонов.** В базовом расписании закачка двигалась шагами 5, 10, 15, 20, 25 м³/сут при медиане нагнетательной 30 м³/сут (`04_models.md` §3, §8) — исторические изменения режима порядка 17–83% от уровня скважины. Это не доказательство линейности и замер не заменяет, но задаёт диапазон, внутри которого объект заведомо эксплуатировался.

### 8.4 Не решено

- Амплитуда не замерена: протокол §8.3 требует прогонов и упирается в §4.8.
- Стоимость плана не оценивается, пока не замерено реальное время прогона OPM. Число прогонов задаётся шириной окна: на 27 активных нагнетательных план короче, чем на 41.
- Сколько окон нужно и где резать границы. Первое окно — начало управления, там дисконт весит в 5.5 раза больше (`04_models.md` §3); сколько матриц потребуется дальше, покажет замер расхождения между окнами. **[гипотеза]**

## 9. Генератор датасета

```
PerturbationPlan → [Schedule] → validate_static == [] → мост → [(Schedule, StateAtDate, IntervalResponse)] + метаданные
```

Каждое возмущённое расписание проходит `validate_static` (§7.1) до того, как на него тратится OPM-прогон: дешёвая проверка отсекает структурно невалидные сценарии раньше дорогой (`04_models.md` §1.1: минуты на прогон).

### 9.1 План обязан покрывать события, а не только уровни **[выбор]**

В базовом расписании **нет ни одной автономной остановки**: все 30 `SHUT` — добывающая сторона перевода под закачку, и режим меняется в 0.85% записей у добывающих (`04_models.md` §8). Датасет, построенный как LHS вокруг базы, не покажет модели ни самостоятельных остановок, ни резких переключений — а оптимизатор будет делать ровно это.

Обязательный состав:

| Вид | Зачем |
|---|---|
| LHS по уровням уставок | базовое покрытие пространства режимов |
| Заведомо недостижимые уставки | иначе модель выучит тождество «цель = факт» (§5.4) |
| Сценарии с автономными остановками и запусками | база этот рычаг не использует вообще |
| Переводы под закачку в разные даты, **только при `allow_conversion_retiming = true`** | тайминг перевода дискретен и дорог (`04_models.md` §4), но физическая экспансия переноса не определена (см. ниже) |

Фиксированный слой дека (§2.1) во всех сценариях датасета одинаков: возмущается управление, а не программа ввода скважин и перфораций. Иначе часть разброса отклика объясняется не тем, чем управляет агент.

**`allow_conversion_retiming` — флаг конфигурации, по умолчанию `false` **[решение, принято 14.08]**.** У 10 переводов после t0 в базовом расписании часть привязанных `COMPDATMD` стоит на той же дате, что перевод (`04_models.md` §3). Если оптимизатор или генератор датасета переносит дату перевода, неясно, переезжает ли связанное изменение перфорации вместе с ней, остаётся на исходной дате или не входит в сдаваемый файл вовсе — вопрос открыт (`06_open_questions.md` §3.11). Пока ответа нет, генерировать сценарии с retiming — значит производить физически неоднозначные деки, которые нечем однозначно эмитировать ни в `OpmDeckEmitter`, ни в `SubmissionEmitter`. Флаг снимается в `true` только после ответа организаторов; до этого 10 базовых дат переводов в датасете фиксированы, возмущается только их наличие/отсутствие как события, но не дата.

### 9.2 Метаданные прогона **[выбор]**

На каждый прогон: seed, статус из `RunResult` (§4.4), доля недостижимых уставок, флаг синтетики. Флаг синтетики в этом канале всегда ложный — синтетические данные в метрики качества не допускаются (§1.1).

## 10. Внешний цикл верификации

Без него оптимизатор находит артефакт суррогата, а не режим пласта. Организаторы называют это одной из трёх вещей, определяющих исход [Лек.37, Лек.44; `01_track2_spec.md` §0].

### 10.1 Схема раунда **[выбор]**

```
раунд r:  оптимизатор ищет θ на суррогате внутри области доверия
          top-k по предсказанному ЧДД → прогон на OPM → истинный ЧДД
          сошлось  → область расширяется
          разошлось → область сужается, k прогонов уходят в обучающую
                      выборку, суррогат дообучается
конец цикла: лучший кандидат по всем раундам переоценивается последней
          версией суррогата и последней областью доверия, возвращается
          self_consistent (§6.5) — это внутренний выбор кандидата,
          НЕ то же самое, что финальная сдача (§10.5)
```

Переоценка последней версией суррогата обязательна внутри цикла: кандидат найден суррогатом версии `r`, а к концу цикла обучение ушло на раунд `r+1`. Без переоценки цикл выбирает кандидата по модели, которой уже нет. **Это не заменяет обязательный финальный OPM-прогон (§10.5)** — суррогат, каким бы согласованным он ни был сам с собой, не является источником сдаваемого числа.

### 10.2 Область доверия — это детектор выхода за диапазон **[выбор]**

Кандидат допустим, пока `ood_score ≤ τ`. Детектор мы обязаны построить и так (§5.2), отдельного механизма области доверия не требуется — расширение и сужение это движение порога `τ`.

### 10.3 Побочный результат — сдаваемые метрики **[факт]**

Таблица «предсказанный ЧДД против фактического» по всем проверенным кандидатам и есть метрики качества суррогата, требуемые к сдаче [Онб.15]. Отдельно считать не нужно.

### 10.4 Не решено

- Чем измерять «прогноз сошёлся»: абсолютное отклонение ЧДД, ранговая согласованность top-k или оба порога сразу. Не замерено. **[гипотеза]**
- Дообучение внутри цикла ломает воспроизводимость, если не зафиксированы порядок раундов и seed'ы. Закрывается §11, но проверить отдельно.

### 10.5 Финальная сдача — provenance от расписания до заявленного числа **[выбор — инженерный гейт; обязательность вытекает из факта дисквалификации, Онб.14]**

Правило дисквалификации — факт от организаторов. Конкретная форма гейта ниже — наше инженерное решение о том, как этому факту не проиграть; **пересматриваемое по механике, не по цели**. До 14.08 §10.1 говорило о переоценке «последней версией суррогата», из чего можно было прочитать, что цикл верификации сам по себе достаточен для сдачи. Это не так — цикл верификации выбирает кандидата, сдача проверяет его ещё раз, целиком, на настоящей физике.

**Гейт устроен в два независимых звена, и они закрывают разные риски:**

```
Schedule* (итог цикла верификации, θ*)
canonical_schedule_hash = hash(Schedule*)                       (§2.3)

validate_static(Schedule*) == []                                 ── обязательный гейт до любого эмита

┌─ звено А: OPM-верификация (реализуемо сейчас) ─────────────────────────────┐
│  OpmDeckEmitter(Schedule*)  → OPM-дек, content_hash_opm                    │
│  Runner                     → OpmRunArtifact = RunResult{                 │
│                                  run_id, status,                          │
│                                  canonical_schedule_hash,                  │
│                                  deck_hash, summary_hash,                 │
│                                  artifacts }                              │
│                              + { content_hash_opm }  ── единственное новое│
│  требуется: status == OK                                                  │
│  ResponseLoader              → ResponseArtifact{                          │
│                                  source_run_id = run_id, response_hash,   │
│                                  StateAtDate, IntervalResponse }          │
│  validate_dynamic             == []                                       │
│  Economics                    → FinalNpvArtifact{                          │
│                                  npv_table, npv_methodology,              │
│                                  source_run_id, source_response_hash,     │
│                                  economics_config_hash,                   │
│                                  methodology_version_hash }               │
└──────────────────────────────────────────────────────────────────────────┘

┌─ звено Б: сдача организаторам (заблокировано, §3.1) ───────────────────────┐
│  SubmissionEmitter(Schedule*) → submission-файл, content_hash_submission  │
│  SubmissionArtifact{ canonical_schedule_hash,                             │
│                       content_hash_submission }                          │
│  не реализуется, пока формат `wells_schedule.inc` не подтверждён          │
└──────────────────────────────────────────────────────────────────────────┘
```

**`OpmRunArtifact` не заводит нового поля для хеша расписания.** `RunResult` (§4.4) уже несёт `canonical_schedule_hash` прогнанного расписания — это ровно то же значение, которое нужно для тождества ниже, отдельное имя `source_schedule_hash` было бы дублирующим полем с тем же смыслом под другим именем. Единственное, что `OpmRunArtifact` добавляет к обычному `RunResult`, — `content_hash_opm`: хеш байтов сгенерированного OPM-дека целиком (статика + расписание), а не то же самое, что `RunResult.deck_hash` (только статическая часть, используется в ключе кеша §4.5) или `RunResult.canonical_schedule_hash` (семантический хеш `Schedule`, не файла).

**Обязательные тождества звена А** (реализуемо и проверяется уже сейчас):

| Тождество | Что ловит |
|---|---|
| `OpmRunArtifact.canonical_schedule_hash == canonical_schedule_hash` (заново вычисленный на моменте сдачи) | подменили расписание после последнего прогона |
| `OpmRunArtifact.status == OK` | несошедшийся прогон не может быть источником заявленного числа |
| `validate_dynamic(ResponseArtifact.StateAtDate, ResponseArtifact.IntervalResponse) == []` | сдаваемое расписание не нарушает динамические ограничения на настоящей физике |
| `ResponseArtifact.source_run_id == OpmRunArtifact.run_id` | `ResponseLoader` прочитал артефакты не того запуска |
| `FinalNpvArtifact.source_run_id == OpmRunArtifact.run_id` и `source_response_hash == ResponseArtifact.response_hash` | в `Economics` передали отклик другого прогона или подменённый после чтения |
| `economics_config_hash == hash(economics_projection(финального Config))` и `methodology_version_hash == hash(реализации Методики)` | число пересчитали с другими нормативами или другой версией калькулятора |

**Тождества звена Б**, когда `SubmissionEmitter` появится: `SubmissionArtifact.canonical_schedule_hash == canonical_schedule_hash` и `parse_submission(submission-файл) == submission_projection(Schedule*)`. Первое связывает provenance, второе проверяет содержимое файла: записать правильный хеш рядом с ошибочно эмитированным расписанием недостаточно. `submission_projection` фиксируется только из подтверждённой спецификации организаторов — до ответа нельзя предполагать, включает ли формат историю и фиксированный слой целиком. Это заблокированная задача 62B (`09_tasks.md`), а не работа, которую можно молча забыть до конца проекта.

`canonical_schedule_hash` — единственный связующий идентификатор между звеньями; `content_hash_opm` и `content_hash_submission` — хеши байтов конкретных эмитированных файлов, разные по построению (разные форматы, §4.1) и не обязаны совпадать друг с другом.

Если после финального прогона расписание правится вручную (интерфейс, §12.5) или автоматически (гибридная поправка, `07_concept.md` §6) — `canonical_schedule_hash` меняется, и цепочка перезапускается целиком с `validate_static`. Промежуточные OPM-прогоны из раундов цикла верификации **не годятся** как источник сдаваемого числа, даже если один из них совпал с финальным θ: тождество сверяется по хешу именно того запуска, а не по совпадению θ.

**Чего этот гейт не закрывает.** Звено А защищает от подмены расписания и от заявления числа, посчитанного не той системой (суррогатом вместо OPM). Оно **не защищает** от расхождения между нашим OPM Flow и симулятором организаторов (tNavigator или иной) — это отдельный, отдельно оцениваемый риск высшего приоритета, разобранный в `07_concept.md` §5.2.1 (измерение расхождения через MRST, устойчивый оптимум, вопрос организаторам). Называть финальный OPM-прогон «достаточной защитой от дисквалификации» — ошибка: он устраняет один класс риска (подмена/суррогат), а не оба.

## 11. Конфигурация и воспроизводимость

Обязательный пункт пакета сдачи: файл конфигурации со всеми параметрами, seed зафиксирован в конфигурации, нет неконтролируемых случайных параметров [Онб.14].

### 11.1 Правило **[выбор]**

**Ни один компонент не читает параметр мимо конфига.** Запуск определяется парой «конфиг + данные организаторов».

### 11.2 Состав

| Раздел | Содержимое |
|---|---|
| seed'ы | глобальный и по компонентам |
| политики | `TaxPolicy`, `InitialEspPolicy`, `QuantizationPolicy`, `LiquidOpexPolicy` (§1.2) |
| **нормативы** | цена нефти, отчисления, OPEX по видам, содержание фонда, стоимости событий, справочник ЭЦН, WACC, налоги — базовые значения из `04_models.md` §4, опционально переопределяемые по годам |
| θ | найденные значения, ≤10 |
| флаги правил | R0–R7 включено/выключено (§6.4) |
| бюджеты | прогонов на раунд верификации, потолок итераций неподвижной точки |
| хеши артефактов | дек, префикс истории, `SummarySpec`, `Groups`, версия датасета, чекпоинт суррогата |

**Раздел `нормативы` добавлен 14.08 — раньше отсутствовал.** Методика прямым текстом называет свои значения «базовыми», допускающими изменение по годам в зависимости от условий сценария (`04_models.md` §4). Держать их константами внутри кода `Economics` означало бы, что смена сценария требует деплоя, а не правки конфига — прямое нарушение правила §11.1 «ни один компонент не читает параметр мимо конфига».

**`economics_config_hash` (§10.5) — это хеш подразделов «политики» и «нормативы» этого конфига**, не хеш конфига целиком: θ и флаги правил не влияют на то, как считаются деньги по уже готовому отклику, и включать их в хеш означало бы, что любая правка оптимизатора ложно инвалидирует уже проверенное число. `methodology_version_hash` конфигом не покрывается — это хеш версии кода `Economics` (формул, а не чисел), фиксируется отдельно при сборке.

### 11.3 Побочный эффект

Хеш выданного дека в конфиге доказывает, что расчёт шёл на данных организаторов, — прямое требование «нельзя подменять исходные данные организаторов своими» [Онб.14].

## 12. Интерфейс

Требование жёстче обычного: прямой источник баллов, и организаторы отдельно назвали антипаттерн — «не должен быть набор исключительно некоторых элементов интерфейса… и в итоге кнопочка, которая позволяет скачать расписание» [10.08 37:11].

### 12.1 Интерфейс не вычисляет **[выбор]**

Все величины приходят готовыми. Собственный расчёт ЧДД, обводнённости или компенсации запрещён: это вторая реализация Методики, которая разойдётся с первой (§1.3).

### 12.2 Читает артефакт прогона, а не живую систему **[выбор]**

```
RunArtifact = {config_hash, Schedule (оба слоя), StateAtDate, IntervalResponse,
               NPV-таблица, Trace, Groups, λ + окно применимости, Constraints,
               флаги converged / self_consistent,
               final_npv: FinalNpvArtifact | null}
```

`final_npv` заполнен только у одного артефакта в библиотеке — того, что прошёл финальную сдачу (§10.5). Остальные сценарии «что если» его не имеют: библиотека артефактов иначе не отличима от списка равнозначных гипотез, а сданный вариант должен быть виден в интерфейсе как единственный с реальным provenance до OPM, а не как ещё один прогноз.

Три следствия. Демонстрационный запуск на защите укладывается в отведённые минуты, потому что воспроизводится готовое [10.08 22:29]. Разработка интерфейса идёт против схемы артефакта и не ждёт ни оптимизатора, ни OPM. Сценарии «что если» становятся библиотекой артефактов, между которыми переключаются.

### 12.3 Главный вид — граф влияния, карта вторым **[решение, принято 13.08]**

Центральный тезис заказчика: пространственная близость не означает гидродинамическую связь [12.08 27:13]. Главный вид это и показывает: скважины расположены по измеренной λ, а не по метрам — соседи по карте расходятся, связанные через пласт сближаются. Поверх — нарезка на участки (`07_concept.md` §6).

Карта месторождения — второй вид, **2D в координатах устьев** с переключателем пласта.

Объёмной сцены не будет. Обоснование замерами: медианная суммарная вскрытая длина 7.4 м при медианном горизонтальном смещении ствола 349 м на ~1200 м вертикали (`04_models.md` §1.1). В трёхмерном изображении каждая скважина — наклонный ствол длиной больше километра, у которого работают семь метров; вертикаль занята нерабочей частью. Дополнительно: объёмный куб визуально обещает моделирование пласта, от которого мы отказались сознательно (`07_concept.md` §5.1).

Разрез по вертикали — отдельный плоский вид по требованию, не сцена.

### 12.4 Взаимодействие определено, а не подразумевается **[выбор]**

Требование звучит как «вы можете с этими скважинами взаимодействовать, смотреть их параметры и режимы» [10.08 37:11]. Ни карта, ни граф сами по себе ему не отвечают — отвечает список ниже.

| Действие | Что происходит |
|---|---|
| Бегунок по 225 управляющим шагам | состояние фонда на выбранном шаге, воспроизведение подряд; на последнем шаге показывается состояние без интервала и денег (§2.2), и это подписано, а не выглядит как нулевой месяц |
| Клик по скважине на шаге `t` | доступность, роль, статус, уставка, **фактический дебит и отношение факт/цель**, обводнённость, забойное давление, накопленная добыча, **сработавшее правило из `Trace` с числами**, текст объяснителя |
| Выделение скважины | подсветка её группы и соседей по λ выше порога, с указанием окна, в котором λ измерена |
| Сортировка фонда | по вкладу в ЧДД из поскважинного разложения (§3.3) — «кто жрёт деньги» |
| Переключатель пласта | смена отображаемого объекта на карте |
| Редактор `Constraints` | порождает документ (§6.3), переключает артефакт из библиотеки сценариев |

Агрегаты поля на каждом шаге: отбор, закачка, компенсация, накопленный ЧДД, **число действующих скважин**. Последнее меняется не только по нашим решениям: 22 скважины вводятся деком внутри горизонта (`04_models.md` §3), и на карте они до своей даты показываются как невведённые, а не как остановленные.

### 12.5 Противоречие «без ручного вмешательства» снято **[выбор]**

Требование работать без ручного вмешательства после запуска [Онб.12] конфликтует с интерактивностью только на вид: интерфейс задаёт **вход** до запуска и показывает результат после, в ход расчёта не вмешиваясь. Согласуется с разомкнутой валидацией — вмешиваться там всё равно некуда.

Снимает открытый вопрос `06_open_questions.md` §3.9.

### 12.6 Не проверено

- Координаты устьев — метры в локальной системе; масштаб, ориентация и разброс не сверялись. Карта может оказаться комком точек.
- Соответствуют ли регионы в `Model_Z_regs.inc` двум пластам из лекции — парсингом не подтверждено.
- Размер `RunArtifact` в браузере. `StateAtDate`/`IntervalResponse` и трасса на глаз мелкие, оценки нет.
- **Как организаторы читают слово «сцена».** Если под ней подразумевается объём, плоская карта прочитается как недоделка независимо от содержания. Вопрос стоит задать. **[гипотеза]**

## 13. Устойчивость: две разные величины

Устойчивый оптимум объявлен несущим: при разомкнутой валидации ошибка суррогата уходит до конца горизонта без шанса на исправление (`07_concept.md` §5.1.4). Принцип был принят раньше, метрики не было.

**Величин на самом деле две, и склеивать их нельзя:**

| | Что меряет | Чем меряется |
|---|---|---|
| **Адаптивность политики** | плохо ли правило перерешает задачу при других условиях | батарея `Constraints`, §13.1 |
| **Хрупкость к ошибке суррогата** | уводит ли ошибка модели найденный план в плохую область | внешний цикл верификации: предсказанный ЧДД против фактического на OPM (§10) |

Батарея не меряет вторую: во всех её сценариях работает один и тот же суррогат с одной и той же ошибкой. Обратное тоже верно — цикл верификации ничего не говорит о поведении при новых ограничениях. Раздел ниже — про первую.

### 13.1 Ось — возмущение мира, а не параметров **[решение, принято 13.08]**

Возмущать θ бесполезно по другой причине, чем записывалось раньше. Формулировка «у правила с ≤10 параметрами острых пиков нет по построению» **неверна**: пороги, гистерезис, квантование уставок и границы типоразмеров ЭЦН делают ЧДД кусочно-постоянным по θ, и разрыв возможен при одном-единственном параметре. Малое число ручек уменьшает размерность поиска, а не негладкость. Возмущать условия надо потому, что тестовый кейс приходит именно в виде условий, а не в виде другого θ.

```
FragilityBattery = версионированный набор возмущений Constraints + seed
regret(θ, s)     = ЧДД лучшего плана для сценария s − ЧДД нашего плана при θ
```

Каждый сценарий: новые `Constraints`, политика перерешает (§6.5), считается ЧДД. Разбивка по сценариям обязательна — она нужна интерфейсу и защите, чтобы предъявить, на каком сценарии план проседает сильнее всего.

**Сравнивать с номинальным ЧДД нельзя.** Сценарий «половина фонда в ремонте» просядет у любого плана, и величина просадки скажет о тяжести сценария, а не о качестве политики. База сравнения — свой ЧДД для каждого сценария: тот же контур, перезапущенный с оптимизацией θ под этот сценарий. Разность и есть regret; он и ограничивается порогом.

### 13.2 Состав батареи **[выбор]**

Из типов возмущений, названных организаторами (`01_track2_spec.md` §9): выпадение скважин на ремонт или аварию, ограничение по закачке в конкретном году, ограничение по жидкости, инфраструктурные лимиты, ограничение по обводнённости.

Батарея — набор документов `Constraints` (§6.3), пишется без единого прогона. Побочно она наш единственный прокси невиданного тестового кейса.

### 13.3 Форма — ограничение, а не штраф **[выбор]**

Максимизируем ЧДД при условии, что regret не превышает порога ни на одном сценарии батареи.

Штраф добавил бы одиннадцатую подгоняемую ручку сверх ≤10. Ограничение не добавляет, и порог берётся из формулировки организаторов, а не подгоняется: ошибка не должна превращаться «из условных 10% в 1000%» [10.08 23:38].

Отсюда форма возврата оптимизатора (§6.1): `feasible` и `violations_by_scenario` вместо скаляра. Скаляр вынудил бы свернуть ограничение в штраф — ровно то, чего этот раздел избегает.

### 13.4 Батарея делится на dev и holdout **[выбор]**

Оптимизация идёт по первой части, отчёт — по второй. Без разделения переобучимся на собственную батарею и получим устойчивость, которой нет.

### 13.5 Чего метрика не покрывает

**Расхождение симуляторов.** Оно не лечится возмущением условий — там другая физика. За него отвечает отдельный ход: прогон одного расписания через OPM и MRST (`07_concept.md` §5.2.1). Смешать эти две вещи легко, и тогда обе окажутся непокрытыми.

### 13.6 Не решено

- Порог допустимого regret в процентах. Формулировка организаторов задаёт порядок, но не число. **[гипотеза]**
- Размер батареи и пропорция dev/holdout.
- Цена сценарного бейзлайна: каждый требует собственной оптимизации θ. Сколько это стоит в прогонах суррогата — не замерено, и от этого зависит размер батареи.
- Числа не считаются, пока нет суррогата: сама батарея пишется сейчас, значения по ней — нет.
