## Обязательная подготовка champion bundle

На машине, с которой показывается интерфейс:

1. Использовать ветку `feat/opm-champion-water-safe` на коммите `08af1c9` или
   более новом проверенном коммите.
2. Убедиться, что существует каталог observation для хеша
   `411bb7207e1689c53d7e38c0c18f6e3b6db8e60857682670f5b4359e0f433ba9`.
3. Проверить совпадение observation с `config/opm-champion.json`:
   `sound=true`, тот же canonical schedule hash, OPM ЧДД
   `7714360866.503498` рублей.
4. Сгенерировать данные интерфейса штатным экспортёром:

   ```bash
   python -m backend.presentation.ui_export.champion_export
   ```

5. Проверить, что экспорт содержит provenance
   `opm-confirmed-water-feedback-champion`, а не
   `policy-search-candidate` или `synthetic-demo`.
6. Собрать интерфейс:

   ```bash
   cd frontend
   npm run build
   ```

7. Открыть каждый экран демо заранее и записать резервное видео длительностью
   не больше двух минут.

Если observation недоступен, не пытаться восстановить его во время созвона.
Использовать fallback-маршрут ниже.

## Ожидаемые вопросы

### Почему результат 7.714 млрд хуже базы около 11.9 млрд?

Короткий ответ: это результаты с разными ограничениями, их нельзя сравнивать
как две точки одной оптимизации.

База в текущем интерфейсе повторяет организаторское расписание без нового
ограничения на источник закачиваемой воды. Water-safe control point ограничивает
закачку доступной добытой водой, использует safety factor 0.85 и пока не
оптимизирован. Его назначение — дать допустимую OPM-опору для следующего
локального поиска.

### Как можно говорить об ошибке 0.52%, если текущий прогноз разошёлся с OPM?

Короткий ответ: 0.52% измерено внутри знакомого распределения, а текущий
кандидат сама модель отметила как OOD.

Это как раз доказательство пользы нового контура. Абсолютную точность нельзя
экстраполировать на неизвестный режим. OOD-score 2.05 запрещает использовать
прогноз 10.535 млрд как итог; поэтому заявляется 7.714 млрд из OPM.

### Зачем тогда вообще нужен суррогат?

Он дешёво отбрасывает слабые варианты, формирует разнообразный shortlist и
уменьшает число OPM-прогонов. Он не имеет права назначать финального победителя
без физической проверки.

### В чём здесь мультиагентность?

Уровни разделяют полномочия: координатор поля управляет общими ресурсами,
групповой уровень распределяет их, исполнители следят за состоянием скважин.
Отдельные функциональные слои проверяют ограничения, экономику и soundness.
Все решения записываются в единый trace.

### Почему не сделать LLM-агента на каждую скважину?

Численные режимы должны быть воспроизводимыми и проверяемыми. LLM медленнее,
не гарантирует численную корректность и не знает физику пласта. Поэтому она
объясняет готовое решение по trace, но не выбирает дебиты.

### Почему групповой уровень сейчас может состоять из одной группы?

Плотная измеренная матрица связности транзитивно соединяет весь фонд. Мы не
рисуем несколько участков только ради красивой схемы. Следующий шаг —
разреживание графа и проверка устойчивости групп между bootstrap-выборками.

### OPM завершился со статусом OK — разве этого недостаточно?

Нет. OPM `OK` означает завершение численного расчёта, но не отсутствие
физически нежелательных режимов. После OPM отдельно проверяются динамические
ограничения, водный баланс, идентичности экономики и происхождение артефакта.

### Это уже финальное расписание?

Нет. Это подтверждённая опорная точка для локального поиска. Финальным станет
только кандидат, который даст sound фактическое улучшение в OPM и выдержит
холодный повтор с полным provenance.

### Почему изменения ещё не в `main`?

Water-safe workflow завершён сегодня в отдельной ветке. Он должен пройти
ревью, перенос observation и проверку воспроизводимости на второй машине.
На чекпоинте статус называем прямо.
