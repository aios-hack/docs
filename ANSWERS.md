## Суррогат

**Что за модель.** Три небольшие нейросети, предсказывающие помесячные траектории 103 скважин
(41 078 + 41 078 + 107 382 = 189 538 параметров, веса усреднения 0.25 / 0.25 / 0.50), плюс
отдельная блочная ядровая голова ЧДД `BlockKernelNpvHead` на 833 обучающих центрах.
Итог: `NPV_pred = 0.8 × прямая голова + 0.2 × экономика предсказанной траектории`.
→ `backend/contexts/surrogate/application/model.py`, `backend/contexts/surrogate/domain/npv_block_head/`, `SURROGATE_DEFENSE.md` §6–7

**На чём обучена.** 700 записей расписаний, 698 уникальных; разбиение по целым расписаниям
490 / 105 / 105. Отклики получены настоящим OPM Flow, не выдуманы. Соответствие метки
проверяется тройкой `source_dataset`, `scenario_id`, `canonical_schedule_hash`; одинаковые
канонические хеши в train и validation запрещены.
→ `SURROGATE_DEFENSE.md` §9

**Метрики.** На историческом test-наборе бленд: Spearman **0.8602**, precision@5 **0.80**,
MAE 42.61 млн ₽, P95 относительной ошибки 1.077%.
→ `RELEASE_SURROGATE_20260906.md`

**Чего НЕ умеет — говорим сами:**

- **Действующие production-веса обучены с `ranking_loss_weight = 0`**, отбор эпохи по `loss`,
  параметризация `absolute`. Ранговый член тренер умеет, но в обучении этих весов он не
  участвовал. Ранговое качество даёт бленд с экономической головой, а не ранговый лосс.
  → `backend/contexts/surrogate/application/model.py`, поле `Settings.ranking_loss_weight` со значением `0.0`
- **Лаг λ в признаки нейросети не заводится.** В рабочем поиске `lambda_edges` передаются
  пустыми. Явного признака времени после последнего события и обучаемой модели лага в
  суррогате нет. λ использует политика, а не сеть.
  → `backend/contexts/optimization/application/environment.py`, `lambda_edges=()`
- **Слепой тест 2017: ошибка предсказания ИЗМЕНЕНИЯ ЧДД — 97.84%.** Модель ожидала
  −0.241 млн ₽, OPM дал −11.121 млн ₽. При этом ошибка полной суммы ЧДД — **0.1186%**.
  Малая ошибка суммы маскирует слабую оценку небольшого изменения; тест **не подтверждает**
  точность ранжирования близких по ЧДД планов.
  → `UNSEEN_CASE_2017.md`
- Метрики означают качество предсказания и ранжирования на конкретной популяции расписаний.
  Из них **не следует**, что модель восстановила гидродинамику, идентифицировала геологию
  или перенесётся на другое месторождение.
- Исторический test многократно исследовался и **новым слепым holdout не является**.
- Веса `data/model-production/` и датасет из 700 прогонов **в git не хранятся** и на машине
  разработки отсутствуют.

## Агенты

**Сколько уровней.** Три, жёстко: `FIELD` → `GROUP` → `WELL`. Перечислены в `Level`,
порядок вызова задан константой `LEVEL_ORDER`.
→ `backend/contexts/policy/domain/levels/`, `backend/contexts/policy/domain/agents/registry.py`

**Что решает каждый:**

| Уровень | Агент | Ответственность (из кода, поле `responsibilities`) |
|---|---|---|
| `FIELD` | `FieldCoordinator` | читает лимит закачки поля из `Constraints`, **а не назначает его сам**; считает спрос участка правилом R1 по измеренной λ; раздаёт квоты пропорционально спросу, не превышая лимит; делит лимит жидкости по маржинальной ценности отбора |
| `GROUP` | `GroupAllocator` | видит только скважины своего участка и его квоту; делегирует выбор уставок правилам R0…R7, **своей арифметики не имеет**; масштабирует запрос вниз, если правила запросили больше квоты |
| `WELL` | `WellExecutor` | квантует уставку шагом задатчика, не выпускает отрицательных; держит потолок дебита жидкости методики; **накладывает вето** на решение внутри простоя скважины |

→ `backend/contexts/policy/domain/agents/field.py`, `group.py`, `well.py`

**Как добавить нового.** Реализовать протокол `Agent` (`name`, `level`, `responsibilities`,
метод `propose`) и добавить экземпляр в `DEFAULT_AGENTS`. Реестр при создании **отказывается**
принять агента: без имени, с повторяющимся именем, **без описанной ответственности**
(«назвать его роль на защите будет нечем» — текст ошибки), с неизвестным уровнем или с рангом,
уже занятым на этом уровне («кто кого ограничивает — не определено»).
→ `backend/contexts/policy/domain/agents/registry.py`, `AgentRegistry.__post_init__`

**Как агенты не спорят.** Предложения одного уровня сливаются `merge_proposals`: границы
сходятся к более строгой (`tightened_by`), вето перебивает решения и обнуляет их, каждое
ужесточение и каждое вето оставляет запись в трассе с именем автора.
→ `backend/contexts/policy/domain/agents/base.py`

**Ни одна уставка не попадает в расписание мимо проекции** на жёсткие ограничения — это
доказано не прогоном, а тестом, который читает исходник поиска и проверяет, что другой записи
в `pending` в файле просто нет.
→ `tests/backend/contexts/policy/test_projection_gate.py`

## Геология

**Что измерили.** Матрицу связности λ: влияние закачки нагнетательной на добычу соседней
добывающей. Метод — спланированный ортогональный эксперимент, МНК по строкам матрицы
воздействий с ridge-регуляризацией `1e-6`, перебор лага по R². Устойчивость меряется
**двумя независимыми партиями плана**: `estimate_lambda` требует минимум две и падает, если
их меньше, — «постфактум её проверить нельзя».
→ `backend/domain/connectivity/`, `FAQ.md` §3

**Числа длинного окна (2007–2025):** 103 узла, **2375 ненулевых рёбер**, лаг **0 месяцев**,
устойчивость между партиями **0.5327**, ранг плана 41 при 103 скважинах, число
обусловленности 7.926.

**Границы метода — говорим сами:**

- **Устойчивость 0.53 — это средне, а не отлично.** Воспроизводится примерно половина
  структуры матрицы. Число выведено в интерфейс и лежит в `meta` артефакта, не спрятано.
- **Ранг плана 41 при 103 скважинах:** план разрешает не все направления, часть рёбер
  оценена в подпространстве.
- **Измерений λ два, на разных окнах, и они различаются:**

  | | Окно 2007–2025 | Короткое окно |
  |---|---|---|
  | Выбранный лаг | 0 мес | **3 мес** |
  | Устойчивость между партиями | 0.5327 | **0.7400** |
  | Ненулевых рёбер | **2375** | 177 |

  Согласие на общей подматрице 245 ячеек: Спирмен **+0.1239**, доля совпадающих знаков 0.3224,
  но **пар с противоположным знаком — НОЛЬ**.

  **Как это произносить:** расхождение **структурное, а не смена направления влияния.**
  Ни на одном ребре два измерения не спорят о том, помогает закачка соседу или мешает.
  Низкий Спирмен объясняется тем, что из 245 общих ячеек **162 ненулевые в одном окне и
  строго нулевые в другом** — «на коротком окне связь ещё не проявилась». Короткое окно
  просто видит меньше связей (177 против 2375) при меньшем фонде, зато то немногое видит
  увереннее. Для управления берём длинное окно, потому что горизонт управления — 2007–2025.
- **Ненулевой лаг 3 месяца на коротком окне снимает подозрение,** что нулевой лаг на длинном —
  артефакт кода: код лаг искать умеет и находит.
- Сам артефакт `lambda.json` на машине разработки **отсутствует**: в `data/` лежит только
  `base_run/`. Витрина построена из прогона, которого на диске тоже нет.
→ `FAQ.md` §3, инструмент сравнения — `tools/lambda_compare.py`

## Ограничения

**Что проверяем.** Динамический валидатор по фактическому отклику OPM проходит по списку
`DYNAMIC_CONSTRAINT_NAMES`: лимиты жидкости, лимиты закачки, полы добычи, лимиты обводнённости,
водоснабжение, простои скважин, коридор компенсации, разрез компенсации, пластовое давление,
материальный баланс. Отдельно — статические проверки расписания и пределы забойного давления.
→ `backend/contexts/schedule/domain/validate_dynamic.py`

**Каждое ограничение отчитывается своим статусом** в
`out/runs/<id>/validation/constraints_report.json`: `checked` (проверено, есть число нарушений),
`not_set` (в кейсе не задано), `unsupported` (объявлено, но валидатор не умеет), `waived`.
Пустой список сюда не пишется намеренно: он читался бы как «ограничений нет».
→ `backend/contexts/schedule/domain/validate/`, класс `ConstraintCheck`

**Блокирующее против диагностического.** Блокирующее нарушение останавливает сдачу; сработало
диагностическое — прогон продолжается, замечание попадает в отчёт. Множество блокирующих видов
задано `BLOCKING_DYNAMIC_VIOLATION_KINDS`; каждая запись отчёта несёт поле `blocking` и режим
`enforcement` (`hard` или `diagnostic`).
→ `backend/contexts/schedule/domain/validate_dynamic.py`

**Откуда берутся пределы.** У каждого параметра инфраструктуры есть парное поле
`<параметр>_source` со значением `organizer` (условие организаторов), `diagnostic`
(диагностический ориентир) или `assumption` (допущение нашей стороны). **Для блокирующих
параметров источник обязателен.** Умолчания BHP 50 / 300 бар помечены `organizer` и читаются
из кейса; сами значения приходят из фиксированного слоя дека, а не назначены кодом, —
поэтому перенос на другое месторождение не требует правки кода.
→ `backend/contexts/constraints/domain/constraints.py`, `config/competition-constraints.json`

**Компенсация идёт в режиме `diagnostic`, а не `hard` — и это осознанно.** Вид нарушения
`COMPENSATION_OUT_OF_CORRIDOR` в коде есть и проверяется, но по умолчанию не блокирует:
**наш коридор не измерен**, а база организаторов идёт 1.20…1.46. Блокировать по неизмеренной
границе значило бы отбрасывать планы по нашему допущению. Режим переключается на `hard`
одним полем кейса — тогда виды компенсации добавляются в блокирующие.
→ `blocking_kinds_for_compensation` в `backend/contexts/schedule/domain/validate_dynamic.py`

**`compensation_scope` со значением `groups` не поддержан.** Как и умолчание
`field_and_groups`: `unsupported` даёт всё, кроме `field`. Группового разреза в валидаторе нет,
`C(k)` считается только по всему полю. Это записано в отчёт, а не умолчано.
→ `_compensation_scope_check` в `backend/contexts/schedule/domain/validate_dynamic.py`

**Физгейт требует `PhysicsReport.admissible`,** а это конъюнкция двух условий: **полнота**
(посчитаны все семь инвариантов — `NON_NEGATIVE`, `WATERCUT_RANGE`, `CUMULATIVE_MONOTONIC`,
`SHUT_WELL_FLOW`, `BHP_LIMIT`, `INJECTION_RESPONSE`, `MATERIAL_BALANCE`) **и** отсутствие
блокирующих флагов. **Пропущенный инвариант — не пройденный инвариант.** Из семи шесть
блокирующие; `BHP_LIMIT` — предупреждение, потому что предсказанное забойное вне предела дека
означает смену режима управления в OPM, а не невозможный прогноз.
→ `backend/contexts/surrogate/domain/physics_checks/`

**Годовые лимиты кейса режутся по прогнозу фактического отбора, а не по сумме уставок.**
Итеративно, до 8 раундов, с запасом 0.98; не сошлось — отказ, а не «примерно». Резка по сумме
уставок существует как явный fallback с флагом `setpoint_sum_fallback`, и сравнение с базой,
порезанной так, **отказывается запускаться**: такая база занижена.
→ `backend/contexts/schedule/domain/case_limits.py`, `compare_baseline_to_candidate` в
`backend/contexts/optimization/application/verification_run.py`

## Воспроизводимость

**Как повторить наше число с нуля — одна команда:**

```bash
bash scripts/cold_repeat.sh --run-id <id>
```

Скрипт читает `git_commit` из нашего `claimed_npv.json`, клонирует репозиторий **на этот
коммит**, ставит зависимости в свежий venv, переносит сохранённое расписание (поиск заново
**не запускается** — иначе повторялось бы другое расписание), гоняет `verify` настоящим OPM
Flow и сверяет полученный ЧДД с заявленным. **Код возврата 0 означает разницу ровно ноль.**
→ `scripts/cold_repeat.sh`; в Docker — команда `repeat` в `docker/entrypoint.sh`

**Быстрая проверка без OPM — 10 секунд:**

```bash
aios selfcheck --submission out/runs/<id>/submission
```

Пересчитывает канонический хеш расписания и SHA-256 байтов файла и сверяет их с заявленными.
Измените в файле один байт — код возврата станет ненулевым.
→ `backend/interfaces/cli/selfcheck.py`

**Что заявляется.** Заявленный ЧДД **обязан** быть посчитан по отклику настоящего OPM.
Прогноз суррогата в него не подставляется: `submit` читает `npv_methodology` из
`out/runs/<id>/economics/result.json` и отказывается собирать пакет, если числа нет. Статус
`ready_to_submit` ставит **только** `submit` и **только** после записи файлов.
Цепочка: `searched` → `verified` (или `rejected`) → `ready_to_submit`.
→ `backend/contexts/runs/application/workflow.py`

**Чем подтверждается происхождение.** 12 полей `SubmissionBundle`: два хеша расписания,
заявленный ЧДД, id прогона OPM, хеш отклика, хеш дека, хеш конфигурации экономики, хеш версии
методики, хеш кейса, образ OPM, коммит и время создания. Одиннадцать из них — непустые строки,
и код отказывается «подставлять правдоподобное значение».
→ `backend/contexts/runs/domain/run_result.py`, тип `SubmissionBundle`

**Сколько стоил счёт.** `out/opm-budget.jsonl` — строка на каждый прогон Flow: время,
статус, хеш расписания, кто запустил.
→ `backend/contexts/simulation/infrastructure/runner.py`

**Прирост к базе.** `run compare --run-id <id>` пишет `comparison.json`. Отказывается
сравнивать, если стороны шли не в одних условиях: сверяются `constraints_hash`, `case_hash`,
`deck_hash` и `opm_image`.

**Честно о состоянии:** механизм пакета сдачи есть и проверен тестами; **собранного и сданного
пакета на машине разработки нет**, потому что нет production-весов и `data/base_case/`.
Что именно есть на диске — в [README.md](README.md).
