# Трек 2 — пространство вариантов реализации

> **Статус файла: каталог вариантов, не решения.** Писался до того, как были приняты решения по концепции. Часть вариантов уже отвергнута — отметки стоят по тексту. Принятые решения — в `07_concept.md`, их журнал — там же §9.

Задача: мультиагентная система с суррогатными нейросетевыми моделями. Прогноз динамики параметров → генерация управляющих действий → валидный `wells_schedule.inc` → максимизация NPV на расширенном наборе сценариев.

Ключ: решение раскладывается на **три независимых слоя**. Их выбирают отдельно, комбинации перемножаются.

---

## Слой 1. Суррогатная модель

| Вариант | Что это | Данных нужно | Плюсы | Минусы / риски |
|---|---|---|---|---|
| **CRM** (Capacitance-Resistance Model) | Материально-балансовая редуцированная модель, коэффициенты связности нагнетательная↔добывающая | ~10¹–10² прогонов, часто хватает истории | Обучается за минуты, интерпретируема, почти не переобучается | Грубая, плохо ловит нелинейности, обводнение только через эмпирику (Koval / Buckley-Leverett) |
| **POD / DMD / ROM** | Редукция порядка по снапшотам поля | ~10² прогонов | Физически обоснована, быстро | Плохо экстраполирует на новые управления |
| **LSTM / TCN / GRU по скважинам** | Временные ряды дебитов/давлений на скважину | ~10²–10³ | Простая реализация, хорошо для покважинной динамики | Не видит интерференцию скважин напрямую |
| **GNN** (скважины = узлы, связность = рёбра) | Графовая сеть поверх скважинного графа | ~10²–10³ | Ловит интерференцию, **масштабируется на новое число скважин** — прямо в названии трека | Нужно задать граф (связность из геологии или обучаемая) |
| **FNO / U-Net / 3D CNN по сетке** | Полнополевой нейрооператор, предсказывает поля давления/насыщенности | ~10³–10⁴ | Максимальная точность, эффектно | Данных почти наверняка не хватит за 4 недели |
| ~~**Гибрид «физика + NN-остаток»**~~ **ПОНИЖЕН** | CRM как база + сеть учит невязку | ~10² | — | CRM решает проблему нехватки данных, которой у нас нет: симулятор свой и бесплатный. Плюс CRM даёт жидкость, а деньги в обводнённости. Оставлен базовой линией и источником ограничения матбаланса — `07_concept.md` §5.1.3 |
| **Прямая модель `управление → NPV`** | Сеть сразу отображает вектор расписания в NPV + нарушения ограничений | ~10²–10³ | Размерность падает на порядки, **дифференцируема** → градиентная оптимизация за секунды | Теряется интерпретируемость динамики, критерий «качество суррогата» сложнее защитить |

Отдельно: **калибровка неопределённости** (ансамбль моделей, MC-dropout, GP-остаток). Без неё нельзя отличить «сеть не знает» от «сеть уверена и врёт» — а это основа trust region в слое 2.

## Слой 2. Оптимизатор управления

| Вариант | Механика | Плюсы | Минусы |
|---|---|---|---|
| **CMA-ES / Differential Evolution** | Эволюция вектора расписания на суррогате | Не нужен градиент, robustный, легко ставится | Много вычислений суррогата, плохо масштабируется по размерности |
| **Байесовская оптимизация / TuRBO** | GP-модель + acquisition, trust region | Эффективна по числу дорогих прогонов, встроенный trust region | Плохо за пределами ~50–100 измерений управления |
| **Градиент сквозь дифференцируемый суррогат** | Backprop от NPV к вектору управления | Сходимость за секунды — прямой ответ на критерий «скорость расчёта» | Требует дифференцируемого суррогата, застревает в локальных минимумах |
| **RL (PPO / SAC)** | Суррогат = среда, агент учит политику | Адаптивность и устойчивость к возмущениям «из коробки» | Дорог по сэмплам, нестабилен, риск reward hacking по суррогату |
| ~~**MPC (скользящий горизонт)**~~ **ОТВЕРГНУТ** | Каждый шаг: прогноз на горизонт → оптимизация → применить первый шаг → переоценить | — | Организаторы подтвердили **разомкнутую** валидацию: один расчёт по полному расписанию, обратной связи нет. Адаптироваться не к чему, главный плюс исчез. Как внутренний приём построения плана остаётся |
| **MARL (MADDPG / QMIX)** | По агенту на скважину/куст, общий reward = NPV | Формально «мультиагентно», честное решение credit assignment | Самый дорогой и хрупкий вариант, высокий риск не успеть |
| **Offline RL / Decision Transformer** | Учим политику на сгенерированном датасете расписаний | Переиспользует данные генерации суррогата | Ограничен покрытием датасета |
| **Правила + подгонка параметров** **ВЫБРАНО** | Оптимизируем не вектор расписания, а правило, которое его порождает; ≤10 подгоняемых параметров | Переносится на невиданный тестовый кейс, объяснимость и устойчивость оптимума по построению | Потолок выразительности; лечится гибридом «правило + поправка на крупные скважины». Набор правил — `07_concept.md` |

## Слой 3. Агентная архитектура

| Вариант | Структура |
|---|---|
| **Жёсткая иерархия** | Менеджер-месторождение (распределяет лимиты закачки/отбора) → агенты-кусты (локальная оптимизация) → исполнители-скважины (штуцер, вкл/выкл) |
| **Иерархия + критик** | То же + агент-валидатор ограничений и агент-оценщик NPV, возвращающий фидбек наверх |
| **Рыночный / аукционный** **ВЫБРАНО как ядро** | Кусты «торгуются» за общий лимит закачки, цена = предельный прирост ЧДД. Реализовано правилом R1 — `07_concept.md` |
| **LLM-оркестратор** | LLM-менеджер рассуждает и вызывает численные инструменты (суррогат, оптимизатор, валидатор). Даёт объяснимость «почему закрыли скважину» — прямо в критерий защиты |
| **Гибрид** | Численная иерархия для управления + LLM-слой поверх только для объяснений и отчёта |

## Сквозной обязательный компонент: внешний цикл верификации

Независимо от выбора слоёв:

```
оптимизация на суррогате
  → top-k расписаний
  → прогон на НАСТОЯЩЕЙ гидродинамической модели
  → дообучение суррогата на этих точках
  → сужение/сдвиг trust region
  → повтор
```

Trust region по расстоянию от обучающей выборки (или по дисперсии ансамбля). **Без этого цикла оптимизатор найдёт артефакт нейросети, а не режим пласта**: прогнозный NPV вырастет, реальный упадёт. Это главный и самый предсказуемый способ проиграть.

## Критические риски

1. **Эксплуатация суррогата** — см. выше. Происходит гарантированно, не вероятностно.
2. **Голод по данным** — если один прогон гидродинамики идёт часами и не параллелится, FNO/U-Net и MARL недостижимы. Замерить время прогона нужно до выбора архитектуры.
3. **Провал на формате** — невалидный `wells_schedule.inc` обнуляет автоматическую валидацию независимо от качества модели.
