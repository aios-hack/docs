# Порядок выполнения — сквозной список с ответственными

Все задачи проекта в порядке, в котором их можно делать. Номер в скобках — задача из `../context/09_tasks.md`, там же приёмка и контракт. Персональные карточки с ловушками — соседние файлы этого каталога.

**Как читать.** Внутри одного блока задачи идут параллельно у разных людей, порядок между ними неважен. Блок начинается, когда закрыт предыдущий по тем позициям, которые перечислены в колонке «ждёт». Ждать закрытия всего блока целиком не нужно — нужно ждать только свои входы.

**Колонка «статус» — единственное место в репозитории, где живёт прогресс.** Ни `../context/09_tasks.md`, ни персональные карточки его не дублируют: там задача описана и задана её приёмка, а сделана она или нет — только здесь. Две копии статуса разъедутся в первый же день.

Значения ровно три:

| Значение | Когда ставится |
|---|---|
| пусто | не начата |
| `в работе` | сессия открыта, ставит тот, кто её открыл |
| `готово ДД.ММ · <коммит>` | приёмка выполнена **зелёным тестом**, коммит с ней указан |

**`готово` без зелёного теста не ставится.** Не «я закончил», не «вроде работает», не «осталось причесать». Приёмка каждой задачи написана в колонке «Приёмка» персональной карточки — это и есть содержание теста, а не вольная трактовка. Нет теста — статус остаётся `в работе`, сколько бы кода ни было написано.

Ставит статус тот, кто закрыл задачу, последним действием сессии: правит эту строку, коммитит `docs` отдельным коммитом вида `задача N закрыта`. Агенту это входит в промт последним пунктом (см. ниже).

> **Стык, требующий согласования при слиянии (16.08).** Ввод 22 скважин внутри горизонта — не управляющее решение, и контракт прямо запрещает адресовать `ControlEvent` скважине в `NOT_COMMISSIONED`. `OpmDeckEmitter` (задача 2) проводит ввод через `fixed_deck_events` внутренним оператором-маркером `COMMISSION` (в текст дека маркер не попадает, есть тест). Если `schedule/build.py` Савелия моделирует ввод иначе, стыковать надо в `bridge/`: поля контракта под это не заводилось.

> **Открытый вопрос, найден 16.08 при разборе задачи 62: порядок оси скважин расходится между пакетами.** `contracts/schedule.py` объявляет `meta.wells` в **лексикографическом** порядке, и `OpmDeckEmitter` его требует. Но `schedule/build.py` и `schedule/canonical.py` строят ось `sorted(..., key=_well_sort_key)` — числовой сортировкой, где `'2'` идёт раньше `'10'`: на Model_Z это те же 103 скважины в 102 разных позициях. **Порядок входит в `canonical_schedule_hash`**, то есть от него зависит идентификатор, по которому §10.5 сверяет сдачу. Реализации задачи 62 и модуля выравнивания в `main` пока нет; до начала работы интегратор должен выбрать единственный канонический порядок и синхронизировать его с `contracts.canonical_bytes`.

> **Интеграционное состояние на 16.08.** Все пакеты четырёх участников влиты в `main`: расчётное ядро, OPM-мост, связность, политики, устойчивость, инфраструктура суррогата и оптимизатора, UI и LLM. Production-сборка `frontend/` проходит, Dockerfile собирает фронт и Python-часть, а расчёт ЧДД сходится с эталоном до машинной точности. Число тестов здесь намеренно не фиксируется: полный набор зависит от наличия Docker/OPM, данных организаторов и LLM-зависимости; актуальный результат даёт только запуск на конкретном коммите.

**Два исходных рубежа пройдены.** Позиция 33 (задача 7) дала первый прогон OPM и замер времени; позиция 30 (задача 11) закрыла схождение калькулятора ЧДД с эталонным расчётчиком. Датасет добран (700 прогонов) и модель задачи 34 обучена 18.08. Текущий длинный путь — приёмка суррогата против CRM, калибровка внешнего цикла на его числах, слияние ветки в `main` и финальная задача 62.

## Как запускать агента на задаче

### Сессия открывается в `aios`, не в `docs`

Соблазн скормить агенту всю базу знаний перед работой понятен и вреден. `08_contracts.md` — 127 КБ, `04_models.md` и `07_concept.md` — по 60 КБ. Прочитав их целиком, агент истратит бо́льшую часть окна до того, как напишет первую строку, и дальше будет кодить с разбавленным контекстом.

Хуже другое: **в базе знаний лежит история решений, и часть её описывает отменённое.** `05_solution_space.md` — каталог с отвергнутыми вариантами. `04_models.md` §1.1 — конвертация под OPM, работа снята 15.08. Журнал `07_concept.md` §9 — колонка «было» целиком состоит из того, что делать не надо. Агент, прочитавший всё подряд, реализует что-нибудь из этого с приличной вероятностью.

Правильный порядок обратный: **сначала код, потом документация точечно.**

1. Сессия открывается в репозитории `aios`. Его `CLAUDE.md` — инструкция для агента, и она сама спрашивает, чья это сессия, и отправляет в нужную карточку.
2. Агент читает `../docs/assignments/<имя>.md` — только свою карточку целиком.
3. Читает `contracts/README.md` по своим типам и импортирует `contracts/*.py`. Это исполняемая форма контракта, компактнее прозы и проверяется конструктором.
4. В `docs/context/` заходит **только за конкретным разделом**, на который ссылается карточка: «§3.2», «§4.1.1». Не за файлом целиком.

### Одна сессия — одна задача

Не «сделай задачи 3, 4 и 5». Задача из списка выше плюс её приёмка из карточки — это ровно тот объём, который агент удерживает без деградации. Следующую задачу — новой сессией.

Первое действие в сессии, до чтения чего-либо ещё:

```bash
cd aios && .venv/bin/pytest contracts/tests
```

Тридцать зелёных — стартовая точка цела. Красные — значит кто-то поправил контракты, и работать нельзя, пока не разобрались.

### Промт для старта

Подставить имя и номер задачи, остальное не трогать:

```
Ты работаешь в репозитории aios, сессия <ИМЯ>.

Прочитай CLAUDE.md этого репозитория и следуй ему.
Задача на эту сессию — ровно одна: <НОМЕР> из ../docs/context/09_tasks.md.
Карточка с приёмкой и ловушками — ../docs/assignments/<имя>.md, найди там
строку с этим номером.

Правила сессии:
- работаешь только в своих каталогах, перечисленных в карточке;
- contracts/ не правишь ни при каких условиях: нужна правка типа —
  останавливаешься и говоришь мне, какая именно;
- типы импортируешь из contracts, не переизобретаешь;
- моков нет: не можешь посчитать — NotImplementedError, а не return 0.0;
- приёмка задачи — тест в твоём каталоге, и её содержание написано
  в колонке «Приёмка» карточки, а не придумывается;
- в docs/context/ заходишь только за теми §, на которые ссылается карточка.

Начни с прогона .venv/bin/pytest contracts/tests и скажи, что получилось.

Когда приёмочный тест зелёный и код закоммичен — последним действием
открой ../docs/assignments/order.md, найди строку своей задачи и поставь
в колонку «Статус» значение «готово ДД.ММ · <хеш коммита>». Отдельным
коммитом в репозитории docs с сообщением «задача <НОМЕР> закрыта».
Если теста нет или он красный — ставь «в работе» и скажи мне, что осталось.
```

### Что агент сделает неправильно, если не запретить

Три места, где контракт задаёт интерфейс, но не логику, и правдоподобный код будет неверным:

| Ловушка | Как проявится |
|---|---|
| Налог на прибыль помесячно вместо годового | Скомпилируется, тесты пройдут, число разойдётся на любом годе с убыточным месяцем |
| Автомат состояний по расписанию вместо отклика | Выглядит естественнее, даёт другие событийные затраты |
| Храповик ЭЦН без прокрутки истории с начала данных | Типоразмер на 01.01.2007 неверен, ошибка уезжает во все последующие замены |

Ловит их одна вещь — позиция 30, схождение с эталонным расчётчиком. Поэтому её нельзя откладывать: пока она не закрыта, любой код ветки экономики условно верен.

### Что проверить, когда агент сказал «готово»

Тридцать секунд, три вещи:

```bash
cd aios && git diff --stat contracts/ && .venv/bin/pytest
```

Пустой diff по `contracts/` — агент не подогнал контракт под свой код. Зелёные тесты — не сломал чужое. Третье глазами: тест в его каталоге проверяет то, что написано в колонке «Приёмка» карточки, а не то, что удобно прошло. Только после этого статус в таблице выше имеет право стать `готово`.
