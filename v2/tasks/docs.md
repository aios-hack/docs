## D1. Линтер ссылок на файлы в markdown

**Цель.** Тест, который падает, когда markdown ссылается на несуществующий файл.

**Почему.** Это единственная задача очереди, которая не даёт ей протухнуть заново. При переносе кода
в `backend/` 22.08 в документации осталось больше пятидесяти ссылок на удалённые пакеты
(`contracts/`, `bridge/`, `ui/`, `aios_cli/`), и нашлись они только сплошным чтением руками. Ничто
их не проверяло, и после любой следующей перекладки история повторится. Всё остальное в этой
очереди — уборка; D1 — замок.

Отдельная причина делать её первой: D2, D3 и D4 двигают файлы, а значит производят ровно тот класс
ошибок, который D1 ловит.

**Что сделать.**

1. Собрать из всех отслеживаемых `.md` в `aios` упоминания путей в обратных кавычках, оканчивающиеся
   на `.py`, `.ts`, `.tsx`, `.json`, `.sh`, `.inc`, `.md`.
2. Для каждого проверить, что файл существует относительно корня репозитория.
3. Явный список исключений для примеров и путей вне репозитория (`/data/docs/...`, `w:/...`,
   пути внутри образа) — с комментарием, почему конкретное исключение законно.
4. Сообщение падения называет файл, строку и несуществующий путь, а не только факт расхождения.

**Что не делать.** Не проверять ссылки на `docs/` из `aios` и обратно: репозитории клонируются
независимо, и такой тест будет падать у того, у кого нет сиблинга.

**Приёмка.** Тест в `aios/tests/architecture/`. На текущем `refactor` он зелёный (все 172 ссылки
резолвятся); при искусственной поломке одной ссылки — красный с указанием файла и строки. Негативная
проверка обязательна: зелёный линтер без неё ничего не доказывает.

## D2. Один канон «что мы строим»

**Цель.** Один документ на вопрос. Сейчас на вопрос «что это за система и зачем» отвечают шесть.

**Почему.** Замер: `docs/README.md` (170 строк), `docs/context/07_concept.md` (373),
`docs/context/10_solution_from_zero.md` (341), `aios/README.md` (291), `aios/DESIGN.md` (235),
`aios/PRODUCT.md` (48). Каждый расходится независимо, и правило старшинства при противоречии
существует ровно одной фразой в `aios/CLAUDE.md`. Это и есть машина расхождений: два репозитория,
описывающих один продукт.

Отдельно: `context/10_solution_from_zero.md` — лучшее в проекте объяснение системы обычными словами,
от задачи до честного текущего состояния, — **до сих пор не в git**. Его нет ни у кого, кроме одной
рабочей копии.

**Что сделать.**

1. `10_solution_from_zero.md` закоммитить прежде всего остального, отдельным коммитом.
2. `docs/README.md` превратить в указатель на два экрана: какой вопрос в каком файле, кто владелец,
   что делать при противоречии. Никакого содержания в самом указателе.
3. Каждый оставшийся документ открывать строкой о том, чего он **не** покрывает, и ссылкой на того,
   кто это покрывает.
4. `aios/DESIGN.md` и `aios/PRODUCT.md` разобрать: продуктовая часть — в `docs`, инженерная — в
   `aios/ARCHITECTURE.md`, дубли удалить. В `aios` остаются `README.md` (установка, запуск, вход-выход),
   `ARCHITECTURE.md` (слои) и `CLAUDE.md` (правила для агента).
5. Правило старшинства из `CLAUDE.md` перенести в указатель и оставить в `CLAUDE.md` ссылку.

**Что не делать.** Не сжимать `context/08_contracts.md` (1 058 строк). Это спецификация с
обоснованиями, и обоснования — единственное, что не даёт по третьему разу переспорить решение.
Сжатие такого документа означает потерю «почему», после чего его пишут заново.

**Приёмка.** На каждый из вопросов — «что за задача», «как устроено решение», «какие контракты»,
«как запустить», «что сделано» — ровно один файл, названный в указателе. Линтер D1 зелёный. Ни одно
утверждение не удалено без переноса: сверка делается диффом, а не на глаз.

## D3. Транскрипции вывести из пути чтения

**Цель.** Отделить источники от документации.

**Почему.** `context/info/` — 5 565 строк, 45% всей прозы базы знаний. Это сырые транскрипции встреч
и лекций. Удалять их нельзя: на них ссылаются метками `[12.08 чч:мм]`, `[Лек.N]`, `[Разр.N]`, это
провенанс принятых решений. Но лежат они в том же дереве, которое человек и агент читают как
документацию, и попадают в каждый обход каталога.

Вторая причина конкретнее: имена файлов кириллические, и это ломает инструменты уже сегодня —
`git ls-files | xargs wc -l` на них падает.

**Что сделать.**

1. Перенести в `docs/sources/`.
2. Переименовать в ASCII-слаги: `2026-08-12-meeting.md`, `2026-08-10-meeting.md`,
   `lecture-development.md`, `lecture-dl.md`, `onboarding.md`.
3. Шапка в `docs/sources/README.md`: сырое, цитируется по таймкоду, не поддерживается, править
   нельзя — это запись сказанного.
4. Обновить ссылки на старые пути в `context/*.md`.

**Приёмка.** `find docs -name '*.md'` не содержит кириллицы в именах. `git ls-files docs | xargs wc -l`
отрабатывает без ошибок. Все ссылки из `context/` на транскрипции резолвятся.

## D4. Архив v1 в тег

**Цель.** Убрать из рабочего дерева 1 269 строк, действовать по которым запрещено.

**Почему.** `aios/CLAUDE.md` о каталоге `v1/` пишет прямо: «открывать только за историей решения;
планом работ архив не является, и реализовывать что-либо по нему нельзя». Каталог, инструкция к
которому — «не действуй по этому», попадает в каждый grep и в каждый контекст агента. Первая версия
закрыта: 65 задач, персональные пакеты, каталог отвергнутых вариантов.

**Что сделать.**

1. `git tag docs-v1` на текущем состоянии, запушить тег.
2. `git rm -r v1/`.
3. В указателе (D2) — строка о том, что первая версия закрыта и лежит в теге `docs-v1`, с примером
   команды для чтения.
4. Проверить, что действующие документы не ссылаются в `v1/` за содержанием, а только за историей;
   если ссылаются за содержанием — это находка, содержание переносится.

**Приёмка.** `git show docs-v1:v1/assignments/order.md` открывается. В `main` каталога нет. Ни один
действующий документ не ссылается на `v1/` иначе как через тег.

## D5. STATUS: состояние отдельно, находки отдельно

**Цель.** Вернуть `STATUS.md` к таблице на один экран.

**Почему.** Изначальное правило файла — «значений ровно четыре» и ничего, кроме статуса. Сейчас
ячейки «Вне очередей» и половина ячеек очереди G — это абзацы с замерами, гипотезами, числами и
причинами. Состояние (что сделано) смешано с доказательством (как измерено). Каждая новая находка
удлиняет таблицу; 22.08 добавились ещё три строки, и каждая абзац.

Практическая цена: на ячейку таблицы нельзя сослаться, её неудобно диффать, у неё нет ни даты, ни
автора, и параллельные правки в ней конфликтуют.

**Что сделать.**

1. В таблице оставить: задача, кто, одно из четырёх значений, коммит. Больше ничего.
2. Каждую находку вынести в `docs/v2/findings/<дата>-<слаг>.md`: что измерено, чем измерено, число,
   вывод, что дальше. Дата и автор берутся из git, в тексте не дублируются.
3. Из ячейки — ссылка на файл находки.
4. Разнести накопленное: разрыв ЧДД (G9), верификация суррогата (G10), нарушения динамики (G11),
   скважина 71 (G12), невоспроизводимость датасета 700, абсолютные пути в кеше, расхождение λ
   обучающей и измеренной, молчащий OOD-детектор, покрытие λ в правилах R1/R6.

**Приёмка.** `STATUS.md` помещается на один экран. Каждая находка — отдельный файл, на который есть
ссылка из таблицы. Ни одно число и ни один вывод не потеряны при переносе — сверка диффом.

## D6. Правило для датированных снимков

**Цель.** Договориться, куда кладутся документы вида «состояние на дату», чтобы они не копились в
корне.

**Почему.** Сейчас в корнях лежат `docs/v2/AUDIT-20.08.md`, `aios/SURROGATE-REQUESTS-20.08.md`,
`aios/SURROGATE_HANDOFF.md`, а на ветке `origin/docs/surrogate-requests-21.08` тот же файл
переименован в `SURROGATE-REQUESTS.md`. Это по одному документу на передачу работы, и они уже начали
конфликтовать между ветками.

**Что сделать.**

1. Решение: снимок состояния — это находка (D5) либо запись в указателе, отдельного файла в корне не
   заводится. Живущий документ (`SURROGATE_HANDOFF.md`) остаётся один и правится на месте.
2. Существующие снимки разнести по этому правилу.
3. Записать решение в журнал `context/07_concept.md` §9 — иначе через неделю его переспорят.

**Приёмка.** В корнях обоих репозиториев нет файлов с датой в имени. Решение записано в журнале.
